# GLDRUBF Trading Bot v1.0 — READ-ONLY API + PAPER

Исследовательский робот SMA20/50 для GLDRUBF. Получает данные официального API Т-Инвестиций и ведёт **только виртуальную** позицию −1/0/+1 контракт. LIVE-режима, методов выставления/отмены заявок, доступа к портфелю нет.

Реализованы завершённые дневные свечи, UID, официальный календарь, отложенные виртуальные исполнения, Decimal P&L, расходы, финансирование, SQLite-восстановление и журналы. **PAPER/replay не являются полноценным бэктестом или доказательством прибыльности.** Авторизованный API и Windows в этой среде не запускались; автоматические тесты используют искусственные технические данные. [Дополнительный технический аудит и Windows-проверка](docs/TECHNICAL_AUDIT_V1_RU.md). [Первоначальный отчёт](docs/AUDIT_AND_IMPLEMENTATION_RU.md).

## Windows без написания кода

1. Установите Python **3.11+** с python.org (включите PATH). Скачайте ZIP этой ветки GitHub и распакуйте целиком.
2. Дважды запустите `setup_windows.cmd`. Он создаёт `.venv` и запускает тесты. Зависимостей вне стандартной библиотеки нет; токен для тестов не нужен.
3. Для виртуальной торговли запустите `run_paper_windows.cmd`. Введите числовые параметры затрат, виртуального депозита и путь **новой** SQLite-базы. Для продолжения используйте **ту же базу и те же настройки**. SMA20/50 и контрактность не настраиваются.
4. Используйте read-only токен Т-Инвестиций. Программа читает `T_INVEST_TOKEN` из окружения. Если переменной нет, Windows-помощник запросит токен **скрытым вводом** и установит только в окружении своего процесса. Токен не передаётся в аргументах команд, не пишется в файлы/логи, его не нужно отправлять в чат. После завершения процесса ввод потребуется заново.
5. Остановка — Ctrl+C. Не удаляйте базу: это источник восстановления, CSV — экспорт. Вторая копия программы с той же базой блокируется. Не запускайте несколько независимых баз как один виртуальный счёт.

`download_candles_windows.cmd` спрашивает даты и выгружает реальные дневные либо минутные свечи. `replay_windows.cmd` запускает событийный PAPER по **отдельным** свечам/наблюдениям цены и календарю. Значения UID и стоимость пункта GLDRUBF здесь не выдуманы: UID обнаруживается/проверяется API; в API-PAPER текущая стоимость пункта запрашивается через GetFuturesMargin. Для исторического replay стоимость пункта/шаг цены нужно явно подтвердить для своего периода.

Графика нет: состояние выводится в консоли. Операции и результаты — `logs/operations.log`, `fills.csv`, `funding.csv`, `bars.csv`, `quotes.csv`, `summary.json`. Поля `realized_gross`, `commission`, `funding`, `realized_net`, `unrealized`, `equity`, `pending` и время mark разделены. CSV можно открыть в Excel. Деньги в RUB, котировки — в API-пунктах, не автоматически в рублях.

## Правила стратегии и исполнения

- Сигналы прежние: для кросса нужны51 завершённая дневная свеча; SMA20 пересекает SMA50 вверх →LONG, вниз →SHORT;0 означает удержание, а не закрытие.
- API `isComplete=true` и окончание соответствующего официального торгового дня должны быть в прошлом. UTC хранится явно; торговая дата — label провайдера/календаря, не дата часов Windows. Выходные/праздники не угадываются по Mon–Fri.
- Сигнал считается известным после получения данных. Котировка раньше сохранённого времени получения последнего нового бара также не исполняет pending: она могла бы изменить уже начисленное финансирование задним числом. В summary это время — `observation_watermark`. Исполнение — по первой подходящей **наблюдаемой** цене со временем **строго позже** знания сигнала. Same-bar close не становится ценой входа. `--once` может лишь сохранить pending: новая цена появится при следующем запуске/опросе.
- API-PAPER опрашивает LastPrices: это выборка последних биржевых сделок, **не обещание первой сделки биржи после сигнала и не исполнимая Bid/Ask-котировка**. Положительное проскальзывание применяется против позиции. Нет имитации очереди/ликвидности/частичного исполнения реальной заявки.
- Разворот — закрытие старого контракта и открытие противоположного, обе стороны оплачиваются. Никогда не держатся два контракта одновременно. На старте/после простоя история прогревает SMA; непроторгованные кроссы обновляют pending до последнего направления, **не создают сделки задним числом**. Цена для catch-up — только новое наблюдение после получения истории.
- Если данные/календарь пропали, история изменилась, UID/стоимость пункта/конфигурация не совпали, программа не выдумывает данные. Временная API-ошибка вызывает повтор позже, существенная ошибка данных останавливает runner. Уже зафиксированная виртуальная позиция остаётся в базе.

## Расходы — явные параметры, не тариф брокера

- `commission-rub`: фиксированная суммарная комиссия RUB **за сторону одного контракта**. Не заявляется фактическим тарифом Т-Инвестиций.
- `slippage-ticks`: целое неотрицательное количество неблагоприятных шагов цены на каждую сторону.
- `funding-per-contract-day-rub`: фиксированный **исследовательский сценарий** за завершённый торговый день. Положительное значение: LONG платит, SHORT получает. Ноль — явное допущение игнорирования финансирования, не утверждение об отсутствии реальных расходов.
- Альтернатива `funding-csv`: `day,long_cost_rub` для переменных дневных ставок. Ставка начисляется за позицию непосредственно перед официальным завершением дня. Для удержанного дня отсутствующая/изменённая уже применённая ставка блокирует обработку. Финансирование на неторговые даты/внутридневные отдельные события текущим дневным settlement-моделем не воспроизводится.

Это не брокерский variation-margin ledger: ГО, принудительная ликвидация, переоценка изменяющейся стоимости пункта, реальный график/формула финансирования бессрочного фьючерса требуют отдельной верификации. Equity может стать отрицательной; начальный исследовательский баланс не является моделью допуска реальных заявок. При изменении денежной спецификации runner останавливается вместо скрытого пересчёта сохранённых позиций.

## Командная строка

Из корня репозитория:

```bat
.venv\Scripts\python.exe -m unittest discover -s tests -v
.venv\Scripts\python.exe -m src.gldrubf_bot.cli --help
.venv\Scripts\python.exe -m src.gldrubf_bot.cli signals --csv daily_legacy.csv
```

Старый формат `day,close` поддерживается **только для сигналов**. Он не содержит времени доступности/отдельной цены исполнения, поэтому новый PAPER его не использует. Старая `paper_events` база прототипа сохраняется, но автоматически не превращается в историю сделок: создайте новую базу.

Пример выгрузки (даты здесь пример границ, не утверждение о полноте доступной истории; конец исключительно):

```bat
.venv\Scripts\python.exe -m src.gldrubf_bot.cli fetch --from 2026-01-01T00:00:00Z --to 2026-06-01T00:00:00Z --interval day --output data\daily_export
```

Будут созданы `daily.csv`, `calendar.json`, `instrument.json`. Экспорт минутных свечей: `--interval 1min`. Текущая незавершённая минута остаётся явно `is_complete=false`; не используйте её для торгового сигнала. Программа не конвертирует произвольную минутную историю в «официальные дневные сессии» догадкой.

## Форматы replay

`daily.csv` (экспорт API): `day,time,closed_at,open,high,low,close,volume,complete`. Все timestamp с UTC-offset; `closed_at` соответствует `calendar.json`. Свечи должны покрывать все завершённые торговые даты календаря без дублей/пропусков.

`quotes.csv`: `time,price` — отдельные реальные наблюдения цены, отсортированные, с уникальным временем и подтверждённым соответствием тому же UID. Нельзя выдавать автоматически скопированные closes или minute OHLC за tick-by-tick исполнение. Повтор того же timestamp с другой ценой останавливает обработку как неоднозначный порядок.

Для replay нужны `--bars`, `--quotes`, `--calendar`, `--uid`, `--point-value-rub`, `--tick-size`, расходы и база. Полный список — `cli replay --help`. Программа экспортирует результаты технической модели, не достоверность источника CSV. Текущую стоимость шага из API нельзя автоматически приписывать историческому периоду.

## Статус проверки

Для ошибки загрузки `Invalid API JSON` добавлена [безопасная диагностика API](docs/API_HTTP_DIAGNOSTICS_RU.md):
метод, HTTP-статус, Content-Type и категория без токена и тела ответа. REST-хост
сверен с официальным OpenAPI. Новый набор из **82 тестов прошёл на Linux / Python
3.12 и 3.13**; настоящая Windows-выгрузка требует повторной проверки пользователем.

Исправление Windows `WinError 32`: соединения SQLite в legacy-коде и тестах теперь
закрываются явно. **68 тестов прошли на Linux / Python 3.12 и 3.13**; настроена
матрица Windows/Linux CI, её фактический Windows-результат пока не подтверждён.
[Причины по группам ошибок, исправления и логи](docs/WINDOWS_SQLITE_FIX_RU.md).

Исходные 6 тестов и расширенный набор из 62 тестов фактически прошли на Linux/Python. Проверены API-ответы/ошибки через имитацию транспорта, не реальный токен/доступность GLDRUBF. Новые/непонятные детальные интервалы календаря отклоняются, а не угадываются. Перед длительным PAPER нужна проверка реального read-only API/источника цены, UID, дневных сессий и расходов на вашей Windows-машине. См. [отчёт](docs/AUDIT_AND_IMPLEMENTATION_RU.md). Deployment, оптимизация SMA и LIVE не выполнялись.
