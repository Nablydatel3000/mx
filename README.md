# GLDRUBF v1.0 — история, historical replay и Forward PAPER

Существующий робот SMA20/50: прямой архив **GetCandles**, исследовательское
воспроизведение и отдельный Forward PAPER. Максимум один виртуальный контракт
−1/0/+1. **LIVE, брокерские заявки и Sandbox-торговля не реализованы.**

Сигнал: SMA20 пересекает SMA50 вверх → LONG, вниз → SHORT; отсутствие кросса —
удержание. Для кросса нужна 51 завершённая дневная свеча. Стратегия и основной
транзакционный движок сохранены. Исполнение — только по наблюдаемой котировке
строго после знания сигнала, разворот как CLOSE + OPEN с расходами обеих сторон.

## Windows

1. Установить Python 3.11+, скачать ветку fix/issue-2-forward-paper-vps целиком.
2. Запустить `setup_windows.cmd`. Внешних Python-зависимостей нет; тестам токен не нужен.
3. Запустить `download_candles_windows.cmd`: даты, day/1min, предыдущий снимок
   для сравнения либо пустой ввод. Read-only токен вводится скрыто только в
   локальной консоли либо используется T_INVEST_TOKEN текущего процесса.
   Токен не нужно отправлять в Codex, сохранять в файле или передавать в аргументах.

**Day-история запрашивается без прошлого TradingSchedules.** Конкретная выгрузка
на Windows с настоящим API ещё требует проверки. Конец диапазона exclusive и
не позднее текущего времени UTC.

Новая папка data/fetch_... содержит raw/0000.json и другие исходные успешные
ответы, manifest.json с запросами/хешами, instrument.json с текущими метаданными,
candles.json/CSV с нормализацией и validation.json с проверками. Незаполненный
evidence_template.json предназначен для временных подтверждений/допущений.

Папки не перезаписываются. Изменившаяся/исчезнувшая завершённая свеча блокирует
использование нового снимка, сохраняя оба источника. Первое получение без
предыдущего снимка не обнаруживает старые ревизии. Сравнение действует в пересечении
диапазонов; его границы и полнота указаны в отчёте.

Отсутствие свечи не доказывает выходной или отсутствие торгов. Свечи не
достраиваются. isComplete проверяется, но не превращается в выдуманное время
исторической доступности. UTC provider_day не объявляется автоматически
торговой датой GLDRUBF.

## Historical replay

Запуск: `historical_replay_windows.cmd`. Нужны снимок, отдельный JSON с явными
временными допущениями/подтверждениями, независимые наблюдения цены CSV time,price
и явно заданные расходы/историческая денежная спецификация.

В шаблоне нужно заполнить торговые даты, completed_at и available_at каждой
завершённой свечи; указать источник, kind=historical_assumption либо verified,
периоды допустимого моделируемого исполнения, UID/хеш и источник котировок.
Незаполненный шаблон блокируется. [Схема и ограничения](docs/HISTORY_PAPER_V1_RU.md).

При допущениях результат — исследовательский сценарий, не доказанная историческая
исполнимость. Нельзя автоматически копировать closes в цены исполнения.
Сигнал доступен в available_at; котировка с тем же timestamp его не исполняет.
Будущие данные отклоняются.

Старый `replay_windows.cmd` / команда replay сохранены для daily.csv и
подтверждённого calendar.json. Они не строят календарь из новых raw.
Команда signals — legacy-расчёт по day,close, а не допуск к PAPER.

## Автономный Forward PAPER

Запуск: `run_paper_windows.cmd`. Папку начального снимка можно оставить пустой:
робот сам загрузит последние 730 календарных дней. Можно указать существующий
снимок GetCandles, чтобы сохранить его начальную границу и сравнить данные.
Evidence заполнять не нужно. Новая база по умолчанию — `paper_auto_v2.sqlite3`;
старую базу не удалять и не использовать для перехода между режимами.
Нужно явно указать сценарии комиссии, проскальзывания и финансирования.
Также обязателен максимальный возраст завершённой свечи в UTC-часах от метки
GetCandles (`--max-complete-age-hours`). Утверждённого значения по умолчанию нет;
Windows-запускатель запрашивает его. Свежий HTTP-ответ не доказывает свежесть свечей.

Каждый цикл обновляет историю, сохраняет raw и проверки отдельно, сравнивает
завершённые свечи с ранее принятыми. В SMA попадают только `isComplete=true`;
время знания — фактическое получение/принятие свечи. UTC-label, в том числе
субботние и воскресные, сохраняются; перевод в MSK служит отображению и не
объявляет метку биржевой торговой датой. Отсутствующие дни не достраиваются.
Покрытие истории остаётся неподтверждённым и явно отражается в проверках.

При первом запуске история используется **только для прогрева SMA**: позиция flat,
исторические пересечения не создают pending. Робот ждёт нового завершённого
пересечения после сохранённой границы bootstrap. Обычный рестарт сохраняет эту
границу, позицию и pending. Исполнение возможно только по более поздней свежей
котировке, при текущем разрешающем статусе и попадании текущего времени и времени
цены в одно реально полученное окно TradingSchedules. Запрос расписания охватывает
сегодня/завтра, чтобы учесть ночные окна; прошлые расписания не используются.

При временном сбое API цикл повторяется. Закрытый рынок/устаревшая цена приводят
к ожиданию; ревизия, исчезновение принятой свечи или запоздалое добавление внутрь
уже рассчитанной истории останавливают обработку с сохранением позиции.
Перезапуск с той же базой и расходами не дублирует сделки. Один runner на базу.
Ctrl+C останавливает процесс, зафиксированное состояние сохраняется.

Автономный цикл проверен с имитацией API. Новый запуск с настоящим API на Windows
ещё требуется. Точное соответствие DAY-агрегатов торговым сессиям GLDRUBF не
доказано; это исследовательский PAPER. Старый режим с явно заданным `--evidence`
сохранён для отдельных баз. [Аудит, ограничения и запуск](docs/AUTONOMOUS_FORWARD_AUDIT_RU.md).

При `Missing/ambiguous current exchange calendar` запустить
`diagnose_current_sessions_windows.cmd`. Он без исторических дат сравнит текущие
ответы с точным фильтром `FutureBy.exchange` и без фильтра, покажет публичные коды
секций и число совпадений. `exact_matches` — побуквенное сравнение,
`casefold_matches` — сравнение без учёта регистра, используемое для выбора.
Неизвестные имена редактируются в `other`.
Другую секцию он не выбирает и PAPER не запускает. Пока соответствие не доказано,
исполнение остаётся заблокированным. [Разбор и диагностика](docs/CURRENT_SESSIONS_RU.md).

Если оба кода скрыты как `other`, отдельная команда
`diagnose_exchange_codes_local_windows.cmd` покажет фактические идентификаторы
**только в интерактивной локальной консоли**. Она не пишет файлы и отказывается
работать с перенаправлением stdout. PAPER и его публичная диагностика не меняются.
[Короткая инструкция и какие значения передать](docs/LOCAL_EXCHANGE_CODES_RU.md).

Подтверждённое пользователем расхождение регистра кодов GLDRUBF исправлено:
в запрос передаётся исходный exchange; для выбора требуется ровно одно совпадение
после `casefold()`. Alias, trim и подстановка другой секции не применяются.
Проверки days, окон, статуса и котировки сохранены. Новый PAPER на Windows ещё
не принят. [Исправление и тесты](docs/EXCHANGE_CASEFOLD_RU.md).

При неизвестной фазе расписания **не обходить проверку**. Для анализа запустить отдельный
`diagnose_schedule_snapshot_windows.cmd`: он сохранит только поля текущего
расписания в `data/schedule_diagnostics/<UTC-время>/schedule.json` и отдельную
проверку `validation.json`. `parse_day()` и PAPER не вызываются и не меняются.
[Схема, ограничения и передача снимка](docs/SCHEDULE_SNAPSHOT_RU.md).

Для описанных пользователем фаз GLDRUBF парсер теперь строит окна из detailed
`regular_trading_session*` только по явно перечисленным именам; legacy-поля
проверяют границы и ограничивают разрешение. Аукционы/клиринг исключены, неизвестные
типы и противоречивые пересечения блокируют день. Дубли не удваиваются, пропуски
не заполняются. Все окна `[start,end)`, без округления `xx:59:59` вверх.
Исходные JSON не приложены: тесты за 17–19.11 воспроизводят описание пользователя,
не заменяют проверку файлов или Windows/API. [Правила и ограничения](docs/GLDRUBF_DETAILED_PHASES_RU.md).

## Базы, расходы и API

Разным режимам нужны отдельные базы. SQLite закрепляет режим и контекст;
historical-replay, calendar-replay, legacy forward-paper и autonomous-forward-v1
нельзя незаметно смешать.
Формат существующей полной базы проверяется и транзакционно дополняется bootstrap-
метаданными. Позиция сохраняется. Старый pending с неизвестным происхождением
сохраняется, но блокируется до нового подтверждённого пересечения
(`WAIT_MIGRATION_REVIEW`). Pending новой версии штатно восстанавливается и не
дублирует сделки. Повреждённые/неполные журналы автоматически не исправляются.
Для одного виртуального счёта используется та же база и один runner; независимые
базы не нужно воспринимать как единый счёт.

Журналы: fills.csv, funding.csv, bars.csv, quotes.csv, summary.json;
historical-replay добавляет research.json с допущениями и хешами.
SQLite — источник восстановления; CSV — экспорт.

Расходы — явные исследовательские параметры: комиссия RUB за сторону контракта,
неблагоприятное проскальзывание в шагах, фиксированный funding либо CSV.
В автономном режиме финансирование — явно заданная стоимость **за каждую новую
принятую завершённую свечу** при её первом подтверждении, на позицию до этого
момента; это не время исторического клиринга. Начальный прогрев проходит без
позиции. `--confirmation-cost-rub` обозначает именно этот сценарий; в CSV `day`
соответствует UTC-label поставщика. В legacy/replay прежние часы расчёта сохранены.
Это не подтверждённый тариф брокера. Сегодняшняя стоимость пункта не приписывается
прошлой истории. ГО, ликвидации, очередь, bid/ask-spread и полный variation margin
не воспроизводятся. Polling LastPrices не гарантирует исполнимую цену.

REST — шлюз официальных gRPC-контрактов: invest-public-api.tbank.ru/rest, JSON POST,
Bearer. Разрешены только семь read-only методов. PAPER — локальная SQLite-модель;
Sandbox — другой брокерский контур, здесь не используется; LIVE отсутствует.
TLS не отключается, redirects запрещены; ошибки обрабатываются без вывода секретов.

```bat
.venv\Scripts\python.exe -m unittest discover -s tests -v
.venv\Scripts\python.exe -m src.gldrubf_bot.cli --help
.venv\Scripts\python.exe -m src.gldrubf_bot.cli historical-replay --help
```
