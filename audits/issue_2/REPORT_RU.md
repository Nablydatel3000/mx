воспроизводимые дефекты и незафиксированные решения. Аудит не исправляет код и
не выбирает новые правила стратегии. Существующие production-код и тесты
побайтно сохранены. PR #1/main не обновлялись. Деплой, merge и LIVE не выполнялись.
Инфраструктурная фаза 2 этой работой не начата; её проектирование не равнозначно
допуску к автономному исполнению.

A2 — расхождение с README, обещающим now и цену в одном реально полученном окне.
Ни now, ни timestamp цены сами по себе не лежат в gap: дефект именно в переносе
цены между фазами. Существующая свежесть 120 секунд этого не исключает.
В примере fill.time=05:59:58 при обработке в 06:00:00: это timestamp последней
сделки, не фактического получения/виртуального решения. Такое моделирование
уже описано как sampled LastPrice, но не доказывает реальную исполнимость.

## Фактические правила стратегии и цепочка состояния

1. История DAY получается GetCandles чанками 90 дней, с UID и EXCHANGE, без
   optional limit; raw/нормализация/validation раздельны. Дубли конфликтов/ревизии
   завершённых свечей блокируются. UTC provider_day не доказан как торговая дата.
2. API raw received_at → normalized observed_at. В engine попадают только
   is_complete=True. Фактическое первое принятие в ledger становится known_at /
   first_confirmed_at; историческое время доступности не выдумывается.
3. SMA20/50 по float(close) и префиксам завершённых **полученных** свечей; нужны 51.
   previous fast <= slow, current fast > slow → +1; previous fast >= slow,
   current fast < slow → −1. Равенство/нет пересечения → **держать**, не flat.
4. Нет SL/TP/trailing/TTL/лимита удержания и нет очереди исторических сделок.
   Последний crossover заменяет pending; промежуточные недоступные пересечения
   намеренно схлопываются в последнюю цель. Это не потеря очереди ордеров.
   Если в доступном lookback не найден ни один crossover, старт остаётся flat,
   даже когда SMA20 и SMA50 уже расположены по разные стороны без нового кросса.
5. Свежий архив, current_sessions, NORMAL_TRADING/доступность market/API и
   актуальная exchange LastPrice предшествуют observe. Проверки future time,
   max_age и монотонности цены остаются; дефект A2 касается конкретного span.
6. observe требует quote.time строго позже pending_after; повтор того же timestamp
   и цены игнорируется, другой price на том же timestamp блокируется. Максимум
   один контракт −1/0/+1; разворот CLOSE+OPEN, расходы двух сторон. Нет риск/ГО
   допуска по виртуальному cash. Текущий начальный cash по умолчанию 100000 —
   виртуальная настройка, не прочитанный остаток брокера.
7. bars/targets/pending/funding сохраняются атомарно одним batch. Fill, quotes и
   новое состояние — отдельная транзакция BEGIN IMMEDIATE. CSV/log — последующий
   экспорт, **SQLite — источник истины**. Нельзя восстанавливать счёт только по CSV.
8. История прогревается flat без прошлых P&L/fills; затем старая цель может быть
   исполнена текущей ценой. Financing начисляется при принятии каждой новой
   complete свечи на позицию до этого момента: не в реальный клиринг.
   Positive fixed rate: long платит / short получает. При catch-up несколько
   начислений приходятся на момент восстановления. Это явная старая модель,
   а не подтверждённый расчёт GLDRUBF.

A1 соответствует уже документированной реализации cold-start target catch-up.
Требование «пересечение → направление» само по себе не выбирает cold-start policy.
Решение ждать только новых пересечений было бы изменением поведения стратегии;
аудит его не вносит. Нет доказательства, что конкретный сентябрьский crossover
по реальным ценам рассчитан верно: нужен реальный CSV.

## Первый запуск, рестарт и сбои: что проверено дополнительно

[reproduce.py](reproduce.py) — семь групп исполняемых проб. Они не заменяют
приёмочные тесты исправлений: некоторые assert специально фиксируют дефекты.
Данные искусственные, изолированные TemporaryDirectory, нет сети и настоящего
токена. Crash child принимает только маркированную временную audit-БД.

Повторить в Linux из корня репозитория:

```sh
python -W error::ResourceWarning audits/issue_2/reproduce.py
python -W error::ResourceWarning -m unittest discover -s tests -q
```

- Синтетически воспроизведены точные даты 25.09→17.11, один SHORT и отсутствие
  повторного fill после рестарта/повторной котировки. Это доказывает механизм,
  **не вычисление SMA по реальным GLDRUBF CSV**.
- Полный mocked GetCandles → snapshot → autonomous.step воспроизвёл A2/A3.
- Сбой календарного API после коммита свечей сохраняет pending без fill.
  После рестарта и нормальной котировки он исполняется ровно один раз.
- Stale quote, закрытый status, будущая цена и ревизия старой complete свечи
  блокируются; позиция/прошлые fills сохраняются. Incomplete close не входит
  в SMA, переход в complete меняет цель только после принятия.
- Реальный subprocess os._exit внутри незакоммиченной SQLite-транзакции:
  изменение откатывается. os._exit после коммита fill до export: fill остаётся,
  повторная котировка не удваивает его, export восстанавливается из SQLite.
- Это process-crash тест, не тест отключения питания/диска и не Windows/VPS.
  Несколько CSV/summary экспортируются пофайлово: при сбое можно получить разные
  поколения файлов; после восстановления нужна сверка с БД.

На Linux/Python 3.12.14 и 3.13.5 фактически прошли **200 существующих тестов**
и все семь новых audit-probe групп. [Команды/результаты](run_results.txt),

Прямые попытки получить MOEX ISS/карточку GLDRUBF и тарифные страницы Т-Банка
завершились URLError. Контроль тарифа показал proxy tunnel 403 Forbidden;
это ограничение доступа из среды, не отсутствие тарифа и не отказ счёта.
Кандидатный URL PDF в журнале доступа не считается проверенным источником.
Числа tick/fee/funding/ГО не выдумывались; 0.04% из прежних задач не переносится.

До экономической оценки нужны официальный тариф и дата/план, спецификация
контракта/биржевые сборы и формула funding с источником ставок. Нули или fixed
confirmation-cost сохраняют смысл только явно обозначенного технического сценария.
Спред/ликвидность/очередь LastPrice модель не воспроизводит. Ни прибыльность,
ни торговое преимущество этим аудитом не подтверждаются.

## План исправлений и приёмка следующей фазы

Порядок: **A1 — решение → A2/A3 — отдельные согласованные исправления и красные
регрессии → A5/A6 — восстановление/один writer → фаза 2 эксплуатация → smoke →
экономическая приёмка A4**. Не смешивать инфраструктурный PR и изменение стратегии.
A4 не мешает техническому offline smoke с явными нулями, но блокирует экономические
выводы. Каждый выбранный fix должен иметь собственное воспроизведение и границы.

Короткий чек-лист допуска PAPER на VPS (сейчас не выполнен):

- [ ] Согласован cold start / target-age / delayed catch-up; сентябрьский кейс
  повторён на реальном CSV, старое состояние не сбрасывается для «успеха».
- [ ] A2/A3 закрыты тестами границ/пропусков/полноты; нет ослабления fail-closed.
- [ ] Один canonical persistent DB и восстановление transaction/fill/export
  проверены на выбранном Linux stack, включая corrupt DB и повторный запуск.
- [ ] Отдельная ветка/PR фазы 2: один обоснованный supervisor, UTC/time sync,
  graceful shutdown/restart, read-only token через secrets/env без логирования.
- [ ] Health/heartbeat и уведомление STOP/отсутствия обновлений проверяют данные
  и последнюю успешную итерацию; PID сам по себе не считается здоровьем.
- [ ] Проверены ротация/retention, объём raw/CSV/logs, backup и restore SQLite
  с проверкой состояния; immutable источники не удаляются молча.
- [ ] Конфиг расходов/капитала зафиксирован; smoke assumptions отделены от
  подтверждённых тарифов. Реальный VPS/API smoke зафиксирован только после запуска.

Отдельный допуск к будущему LIVE: отдельное согласие и проектирование order API,
подтверждённые тарифы/funding/спецификация/ГО, исполнимый bid/ask и ограничения
риска, сверка реальных позиций/заявок, idempotency и восстановление uncertain
order outcome, отдельная sandbox/контролируемая приёмка. Текущий код LIVE не имеет;
эта фаза не реализована и не разрешена настоящим аудитом.
