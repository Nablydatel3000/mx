# GLDRUBF: PAPER на Linux VPS

Файлы подготовлены для Ubuntu 24.04 LTS, Python 3.12 и systemd. Установка и запуск
на настоящем VPS ещё не выполнялись. Это локальные виртуальные сделки с read-only
API; LIVE и Sandbox не включаются. Формула SMA20/50 сохранена.

## 1. Подготовьте параметры

Нужны read-only токен Т-Инвестиций и отдельный канал уведомлений: Telegram-бот
(его токен и chat ID) либо HTTPS webhook. Вводите секреты только на своём сервере,
не присылайте их в чат и не вставляйте в команды.

Также нужны **прежние** значения капитала, комиссии RUB за сторону контракта,
проскальзывания в шагах и сценария финансирования. Это параметры модели,
не подтверждённые тарифы. При переносе базы они должны совпадать с её настройками.
Фиксированное финансирование в автономном режиме — RUB на новую подтверждённую
свечу, а не биржевой клиринг. Можно использовать прежний CSV вместо константы;
он должен быть доступен пользователю службы по абсолютному пути.

Задайте допустимый возраст последней завершённой свечи **в UTC-часах от её метки
GetCandles**, включая выходные и праздники. Утверждённого значения нет: программа
его не выбирает. Слишком малое значение остановит исполнение на длинном перерыве;
слишком большое ослабит обнаружение устаревшей истории. Без явного значения запуск
блокируется. Задайте срок хранения локальных raw/диагностик в днях: более старые
снимки будут удаляться, кроме последних двух и последних двух успешно проверенных.

## 2. Установите файлы

В терминале **своего** сервера выполните:

```bash
sudo apt-get update
sudo apt-get install -y python3 git ca-certificates
git clone --branch fix/issue-2-forward-paper-vps https://github.com/Nablydatel3000/mx.git
cd mx
sudo bash deploy/linux/install.sh
```

Мастер спросит параметры из пункта 1. Секреты вводятся невидимо. Установщик
не запускает службы и не обращается к брокеру. Код: `/opt/gldrubf/mx`;
настройки: `/etc/gldrubf/paper.json`; секреты root-only: `/etc/gldrubf/api-token`
и `alert-*`. systemd передаёт каждой службе только нужные ей credentials;
токен не попадает в командную строку или Git.

Проверьте синхронизацию часов:

```bash
timedatectl show -p NTPSynchronized --value
```

Должно быть `yes`. При `no` сначала настройте синхронизацию времени на VPS.
Для новой базы переходите к пункту 4. Новая база начинает **без позиции** и ждёт
нового пересечения; отсутствие сделок после прогрева — ожидаемое поведение.

## 3. Если переносите действующий Windows PAPER

Не запускайте параллельно Windows и VPS как один виртуальный счёт. Завершите
Windows-робота через Ctrl+C и дождитесь выхода. Скопируйте его **последнюю целую
SQLite-базу** на сервер как `import.sqlite3`. Не копируйте работающую базу обычным
копированием; если есть WAL/journal или сомнения в завершённости, остановитесь
для проверки, а не выбирайте старую копию наугад.

Из папки, куда скопирован файл:

```bash
sudo install -o gldrubf -g gldrubf -m 0600 import.sqlite3 /var/lib/gldrubf/import.sqlite3
cd /opt/gldrubf/mx
sudo -u gldrubf python3 -m src.gldrubf_bot.vps restore --backup /var/lib/gldrubf/import.sqlite3 --authoritative-ledger
```

`--authoritative-ledger` означает ваше подтверждение, что это полный актуальный
журнал после корректной остановки/сверки, а не резервная копия до последних сделок.
При сомнениях **не используйте этот флаг**: восстановление без него сохраняет
блокировку до сверки. Несовпадение расходов или повреждение журнала блокирует импорт.
Позиция и подтверждённый pending сохраняются. Pending из старого формата с неизвестным
происхождением остаётся заблокирован до следующего нового пересечения:
`WAIT_MIGRATION_REVIEW`. Не удаляйте pending или базу, чтобы обойти ожидание.

## 4. Включите службы и проверьте работу

```bash
sudo systemctl enable --now gldrubf-paper.service gldrubf-health.timer gldrubf-backup.timer
systemctl status gldrubf-paper.service --no-pager
sudo journalctl -u gldrubf-paper.service -n 30 --no-pager
sudo cat /var/lib/gldrubf/health.json
sudo cat /var/lib/gldrubf/monitor.json
sudo cat /var/lib/gldrubf/delivery.json
```

Последние два файла появятся после первого тика таймера, обычно в течение минуты.
Проверьте фактическое получение уведомления. Уведомления о состоянии, сбоях,
восстановлении, PAPER-сделках и резервных копиях идут через отдельную службу;
при ошибках доставки сохраняются для повтора. Возможны повторные уведомления
после сетевой неопределённости. Они не содержат брокерский токен и номер счёта.
Не публикуйте содержимое `/etc/gldrubf/*`.

`WAIT_MARKET` вне разрешённых окон — нормальное ожидание. `WAIT_HISTORY` означает
недостаток завершённых свечей. `WAIT_COMPLETE_HISTORY` — история старше заданного
порога; `WAIT_CALENDAR` — нет подтверждённого расписания. Эти ожидания не дают
разрешения на сделку. Контроль работоспособности учитывает последнюю успешную
проверку данных, а не только наличие процесса. Длительные ожидания данных вызовут
уведомление даже при живом процессе.

Временные ошибки API повторяются без потери позиции. Сбой процесса перезапускается
systemd с ограничением частоты. **STOP / код 78** (данные, конфигурация, SQLite)
не перезапускается автоматически: сначала выясните причину, сохраните журналы,
затем после исправления выполните `sudo systemctl restart gldrubf-paper.service`.
Не удаляйте SQLite и защитные файлы ради запуска.

## 5. Хранение, обслуживание и восстановление

Основная база — `/var/lib/gldrubf/paper.sqlite3`, её нельзя удалять при обновлении.
Журналы/CSV/raw — `/var/log/gldrubf`; `operations.log` ротируется: 5 MiB + 5 копий.
CSV состояния экспортируются заново; источником восстановления служит SQLite.
Срок raw/checks задан вами при установке. journald использует лимиты ОС.
Храните всё на **локальной файловой системе**, без NFS и hardlink базы.

Ежедневная служба создаёт SQLite online backup с проверкой целостности и состояния;
по умолчанию хранит последние 7 копий в `/var/lib/gldrubf/backups`. Проверка вручную:

```bash
sudo systemctl start gldrubf-backup.service
sudo journalctl -u gldrubf-backup.service -n 10 --no-pager
```

Скачивайте проверенные копии на отдельный носитель. Это копии базы, не архив
всех raw/конфигурации; секреты в них не включаются. После потери всего VPS
независимые уведомления с этого же VPS тоже не работают: нужен внешний монитор
провайдера/сервера и отдельная копия данных.

Перед обновлением или ручным восстановлением остановите службы:

```bash
sudo systemctl stop gldrubf-paper.service gldrubf-health.timer gldrubf-backup.timer
sudo systemctl stop gldrubf-health.service gldrubf-backup.service
```

Для восстановления проверенной копии используйте команду `vps restore --backup
/полный/путь/к/копии.sqlite3` от `gldrubf` из `/opt/gldrubf/mx`. **Обычная старая
копия оставляет PAPER на паузе**: в ней могут отсутствовать последние сделки.
Нельзя гарантировать отсутствие повторов, если утрачена часть журнала. Нужна
сверка с последним экспортом/полной базой; автоматического «отката и торговли» нет.
Физически повреждённый файл назначения может потребовать отдельного ручного
восстановления, инструмент не объявляет его автоматически исправленным.

Для изменения настроек при остановленных службах повторите локальный мастер:

```bash
cd /opt/gldrubf/mx
sudo python3 -m src.gldrubf_bot.vps configure
sudo chgrp gldrubf /etc/gldrubf /etc/gldrubf/paper.json
```

После обслуживания включите те же службы из пункта 4. Реальный VPS/API smoke
нужен до приёмки автономной работы. Это не допуск к LIVE и не доказательство
доходности SMA20/50.
