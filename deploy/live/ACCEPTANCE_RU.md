# Приёмка на Jino без торговых заявок

**Новая отдельная ветка fix/live-current-execution-safety:**
[обновление только read-only приёмки](../../docs/live_execution_safety/JINO_READ_ONLY_RU.md).
Переход старой LIVE SQLite на новый fingerprint не реализован и остаётся заблокированным.

**Доступа Codex к Jino нет. Пользователь сообщил о выполненной установке и
реальной read-only проверке; Codex не проверял VPS самостоятельно.** Для уже
установленного контура сначала используйте [обновление диагностики счёта](../../docs/live_acceptance/ACCOUNT_SNAPSHOT_RU.md).
Для подтверждённой ошибки GetMarginAttributes 30051: [причина и следующие действия](../../docs/live_acceptance/MARGIN_30051_RU.md).
Для current_calendar/границ IOC: [безопасная диагностика](../../docs/live_acceptance/CURRENT_CALENDAR_RU.md).
Для holiday_trading_session_morning 21 ноября: [результат проверки источников и блокирующие сведения](../../docs/live_acceptance/HOLIDAY_PHASE_RU.md).
Команды первичной установки ниже — только для новой установки, не поверх существующей.
Этап read-only: без торгового разрешения, LIVE SQLite и включения службы.
PAPER, его SQLite, токен, каталоги и systemd не меняются.

## Минимальные команды

```bash
git clone --branch feature/gldrubf-live-gated https://github.com/Nablydatel3000/mx.git mx-live-check
cd mx-live-check
sudo bash deploy/live/install_readonly.sh
```

Установщик скрыто спросит ID выделенного обычного брокерского счёта. Если API
account ID неизвестен, оставьте пустым: первый счёт автоматически не выбирается.
Создаются отдельные `/opt/gldrubf-live-acceptance/mx`, `/etc/gldrubf-live-acceptance`,
`/var/lib/gldrubf-live-acceptance` и пользователь `gldrubf-live-check`.
Ни systemd-unit, ни торговое разрешение, ни `live.sqlite3` не устанавливаются.
Существующие целевые файлы/команды не перезаписываются.

Токен введите **только на VPS скрытым локальным вводом**:

```bash
cd /opt/gldrubf-live-acceptance/mx
sudo python3 -m src.gldrubf_bot.live_acceptance install-token
```

Credential root-only 0600; токен не попадает в argv, Git, чат или логи.
Wrapper передаёт его непривилегированному процессу через уже открытый stdin:
без временного файла и печати в shell. Окружение очищается. Существующий файл
не затирается; ротация требует отдельной локальной процедуры.

Если ID счёта неизвестен, выполните два дополнительных шага:

```bash
sudo gldrubf-live-check accounts
sudo python3 -m src.gldrubf_bot.live_acceptance account
```

Первая команда только читает GetAccounts и показывает ID в **локальной консоли**,
не сохраняя список. Вторая скрыто запрашивает выбранный ID и меняет только
acceptance-конфиг. Не выбирать счёт наугад; он должен быть выделенным, без
других инструментов, ручных заявок и других ботов.

Проверка и короткая статистика:

```bash
sudo gldrubf-live-check
sudo gldrubf-live-status
```

Полная безопасная диагностика: `sudo gldrubf-live-status --json`.
Для этих команд не нужна никакая LIVE-служба. Прежнюю инструкцию активации
торгового режима на этом этапе не выполнять.

## Что проверяется и сохраняется

GetAccounts/FutureBy, GetPositions/GetPortfolio/GetWithdrawLimits/GetMarginAttributes,
GetFuturesMargin, GetOrders, текущие TradingSchedules, GetTradingStatus,
GetLastPrices/GetOrderBook, DAY GetCandles за 14 календарных дней, GetMaxLots
и GetOrderPrice **для двух контрактов в обе стороны**, операции за последние 7 дней.
GetOrderPrice — оценка, не отправка и не резервирование заявки.
GetOrderState читается только при уже существующем GLDRUBF request ID. Иначе
он помечается not_tested; никаких пробных orders для получения ID не создаётся.

Независимый закрытый allowlist запрещает отправку, отмену, замену заявок и переводы
до HTTP независимо от прав токена. Торговый Engine/Store не запускается, сигналов
и UUID торговых заявок нет. Повтор команды — только повтор чтения.

Сохраняются `report.json` и `attempt.json`: HTTP-статусы/категории, наличие
ожидаемых API-полей и выбранные численные показатели. Нет токена, Authorization,
имён/ID счетов и произвольного тела API. Баланс и позиция — всё равно частные
данные: просмотрите отчёт перед передачей. Для анализа достаточно `report.json`;
не прикладывать credential, конфиг со счётом или SQLite.

Статистика показывает баланс/ликвидность/доступные RUB, позицию, оба ГО, RUB/пункт,
брокерский settled VM и платежи комиссий в указанном образце, число открытых заявок
и исполненных торговых **операций**, не отдельных fills. Это не модельный P&L PAPER.
Недоступные значения не заменяются нулями. Кэш старше 300 секунд помечается
устаревшим; сама команда просмотра не обращается к API.

## Предлагаемые значения вместо null

Устанавливаются только в acceptance-конфиг, не в PAPER или торговый LIVE.
Это предложения для приёмки, а не окончательное одобрение реальной торговли.

| Параметр | Значение | Причина |
|---|---:|---|
| max_complete_age_hours | **96** | Возраст от UTC-метки complete-свечи. Длинные праздники/перерывы блокируются до свежих данных, календарь не выдумывается |
| quote_max_age_seconds | **15** | Строгая свежесть LastPrices/стакана; редкие сделки означают ожидание |
| snapshot_max_age_seconds | **30** | Предел возраста/длительности проверки счёта; медленный API не даёт разрешение |
| margin_stress_multiplier | **3** | Резерв под трёхкратное текущее ГО, не прогноз биржи |
| cash_reserve_rub | **2000 ₽** | Дополнительный запас; не гарантия покрытия любого funding/гэпа |
| max_order_fee_rub | **25 ₽** | Оценка 20,28 ₽ + запас 4,72 ₽. Предел одной заявки из двух контрактов, не тариф. Разворот имеет две заявки |
| max_slippage_ticks | **2** | Жёсткая ценовая граница: при шаге 0,1 это 0,2 пункта от LastPrice |
| order_ttl_seconds | **30** | Предел ожидания IOC-подтверждения в будущем LIVE; не повод перевыставлять |
| poll_seconds | **15** | Несколько проверок в минуту; история в базовом LIVE обновляется не чаще 60 s. Реальные квоты надо проверить |
| min_session_remaining_seconds | **60** | Запас до конца фазы, без гарантии отсутствия любой серверной задержки |

Цена консервативности — возможный отказ: 96 h блокируют длинные праздники,
два ticks могут не вместить спред. Не увеличивать пределы автоматически ради
зелёного отчёта. Все параметры записаны в `config.acceptance.example.json`.

Бюджет **15000 ₽**, цель **2**. Формула базового capital-gate:
`2 × ГО стороны × 3 + 4194,4 × RUB/пункт + 2000 + оценка комиссии`.
При **условных** GO=1400 ₽, Q=1 ₽/пункт и комиссии 20 ₽ нужно **14614,4 ₽**;
при GO=1500 ₽ — **15214,4 ₽**, выше бюджета: отказ. Это иллюстрации, не актуальные
параметры. Реальные числа появятся после пользовательского запроса API.
GetMaxLots проверяется независимо; при лимите 1 объём не уменьшается автоматически.

## Как читать результат

- `read_checks_ok=true` — перечисленные чтения прошли, **не** допуск к LIVE.
  `live_accepted=false` остаётся всегда.
- `market.tradable_now=false` — текущие status/time/price/window gates не прошли.
  В закрытый рынок это ожидаемо; повторить в подтверждённую обычную фазу.
- `blockers` — ошибки HTTP/схемы/свежести/позиции/ГО/лимита двух контрактов.
  Код выхода 2 означает сохранённый отчёт с блокерами, не разрешение игнорировать их.
- `order_state_runtime=not_tested` — существующей заявки нет, фактические stages,
  IOC и торговое recovery не проверены. Создавать пробную заявку на этом этапе нельзя.

Официальный контракт содержит IOC `TIME_IN_FORCE_FILL_AND_KILL=2` для LIMIT,
но read-only status flags не подтверждают поддержку именно GLDRUBF/счётом/секцией.
`FILL_OR_KILL` — другой режим. Реальные IOC/fills/partial/cancel и идемпотентность
неоднозначной отправки остаются до отдельно разрешённого следующего этапа.

## Памятка при остановке

1. Не запускать торговую службу и не снимать блокировки. Диагностика ничего
   не создаёт/не отменяет; PAPER работает отдельно.
2. Посмотреть `sudo gldrubf-live-status`, затем `--json`: метод, HTTP/category,
   `fields_present`. Не выводить token-файл и не включать shell tracing.
   Само `fields_present=false` не всегда ошибка: proto3 может опускать default/
   пустые поля. Важен результат валидатора и список blockers; отсутствующие
   денежные данные нельзя автоматически считать нулевыми.
3. 401/403 — локально проверить права токена/счёта. 400/неизвестные поля —
   сохранить безопасный report для разбора, не угадывать значения. При timeout/502
   после восстановления связи вручную повторить `sudo gldrubf-live-check`.
4. После прерывания/ошибки token/config новая попытка FAILED/RUNNING; старый
   зелёный кэш помечается как предыдущий. Новый успешный check восстановит текущий
   отчёт, не торговую сессию. Код выхода 78 — локальная/неожиданная ошибка.
5. Существующая позиция/заявка — сверка в приложении брокера, без автоматического
   закрытия/отмены. Дефицит средств/лимит 2 не обходить снижением резерва.
6. Если установка прервалась или обнаружены старые команды, не удалять каталоги
   или SQLite. Разобрать конфликт файлов; повторный install не затирает их.

До контролируемого открытия двух контрактов нужны реальный безопасный report,
устранение блокеров, подтверждение финансов/численных политик и отдельный допуск
к тесту IOC/исполнений/восстановления. Этот этап такого допуска не даёт.
