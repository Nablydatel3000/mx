# Безопасное сравнение urllib и curl.exe

Дата: 2026-11-05. Ветка `gldrubf-v1-paper-api`, существующий PR #1.

## Исходные наблюдения пользователя на Windows

- TCP 443 и HTTPS доступны.
- POST FindInstrument без токена через curl возвращает 401.
- `urllib.request.getproxies()` возвращает `{}`.
- Робот с read-only токеном получает 502 / text/html на FindInstrument.

Это ещё не сравнение эквивалентных запросов: различаются клиент и наличие
авторизации. Доступность HTTPS и ожидаемый 401 не подтверждают успешность
авторизованного маршрута API. Причина 502 по этим данным не установлена.

## Запуск

Получить обновлённую ветку/ZIP PR #1. После `setup_windows.cmd` запустить
**`diagnose_api_windows.cmd`**. Ввести read-only токен в скрытом приглашении.
Программа всегда запрашивает его заново, не берёт из T_INVEST_TOKEN, не принимает
его аргументом и не сохраняет. При отсутствии безопасного консольного ввода
останавливается; небезопасного fallback с echo нет.

Выполняется ровно по одной попытке POST FindInstrument каждым доступным клиентом:
сначала urllib, затем curl.exe. Отсутствие curl.exe или сетевой отказ показываются
как безопасная категория; повторов/redirect нет. Настройки торгового робота не
читаются и не изменяются, SQLite и PAPER не запускаются.

После приглашения выводятся только две строки. Пример ниже **искусственный**:

```text
client=urllib http_status=502 category=server_error
client=curl.exe http_status=502 category=server_error
```

HTTP-статус unknown означает отсутствие подтверждённого статуса ответа API.
Код ошибки CONNECT не выдаётся за HTTP-статус API. HTTP 200 / http_ok означает
получение HTTP 200 с JSON Content-Type; тело не проверяется на пригодность свечей.
Токен, Authorization, Content-Type, прочие заголовки, тело, URL прокси, сведения
об окружении и исходный текст исключений не печатаются. Диагностических файлов нет.
Код выхода 0 — оба результата http_ok; 1 — любой другой результат. Launcher
сохраняет код выхода после pause.
Для .cmd сохранён CRLF; Git whitespace-атрибут учитывает CR в конце строки,
сохраняя проверки лишних пробелов и пустых строк.

## Как защищён curl

- Запуск без shell, полный путь curl.exe разрешается через PATH.
- Аргументы только `--disable --config -`. `--disable` первым отключает .curlrc:
  локальная конфигурация не сможет добавить trace/verbose, insecure или redirects.
- Authorization и JSON передаются только в конфигурации через stdin pipe.
  Токена нет в argv, временном файле или передаваемой переменной T_INVEST_TOKEN.
- Токен проверяется по грамматике Bearer, управляющие символы/кавычки отклоняются;
  значения curl-конфигурации дополнительно экранируются.
- Тело направляется в устройство NUL; stderr — в DEVNULL; stdout с ограниченным
  write-out форматом перехватывается. Даже он считается недоверенным: наружу
  проходят только проверенное число статуса и фиксированная категория.
- SSLKEYLOGFILE отключается в отдельном диагностическом процессе/дочернем curl,
  чтобы TLS-сеансовые ключи не записывались на диск.
- HTTPS-only, обычная проверка TLS/сертификатов, отсутствие insecure, redirect и
  fallback на другой хост. Connect timeout curl 10 секунд, общий 20 секунд;
  Python socket timeout 20 секунд, ограничение ожидания subprocess 25 секунд.

В urllib тело не читается; HTTPError/ответ закрываются при любом обычном исходе.
В curl тело принимается только в NUL, не в журнал или Python stdout.

## Что сопоставлено и что ещё может различаться

Одинаковы официальный URL, POST, байты JSON `{"query": "GLDRUBF"}`, токен,
Content-Type, Accept, Accept-Encoding identity, User-Agent Python-urllib текущей
версии Python, Connection close. curl принудительно использует HTTP/1.1, как urllib.
Оба клиента сохраняют свою обычную поддержку прокси; настройки/адреса не выводятся.

Остаются реальные различия реализаций: TLS backend/ClientHello, доверенные корни,
реализация DNS/выбор IPv4/IPv6, определение прокси и маршрутизация. Конкретный TLS
backend Windows curl в этой среде не установлен: нельзя без проверки объявлять,
что это обязательно Schannel. Даже при одинаковых настройках последовательные
запросы могут попасть на разные backend или на временный сбой.

| Результат | Допустимый вывод |
| --- | --- |
| Оба 502 | Ошибка наблюдается в обоих клиентах с авторизацией. Python как причина не доказан; нужно исследовать серверный/шлюзовой маршрут, не менять стратегию |
| urllib 502, curl 200 или наоборот | Зафиксировано различие при сопоставимых HTTP-запросах. Нужна повторная проверка на этой машине и исследование TLS/маршрута/прокси; один запуск не устанавливает причину |
| Оба 401 | Авторизация отвергнута обоими; секрет не публиковать. Это не основание отключать TLS |
| unknown и сетевая категория | Клиент не подтвердил HTTP-ответ API; это не равнозначно серверному 502 |

Неавторизованный curl 401 из прежнего опыта нельзя подменять результатом нового
авторизованного curl. Диагностический запуск не автоматически переключает робота
на curl и не объявляет проблему исправленной. Для продолжения достаточно передать
две безопасные строки результатов, без токена и дампов.

## Проверки

Добавлены 14 тестовых методов, включая подслучаи: скрытый ввод и запрет echo,
инъекции в токен, один вызов каждым транспортом, равенство запроса, stdin-only
секрет, отсутствие секрета в argv/env/выводе, запрет файлов, подавление произвольных
stderr/исключений, статусы одинаковые и разные, TLS/сеть, отсутствующий curl,
закрытие HTTP-ответов, отсутствие retries, CRLF launcher и запуск модуля без консоли.
Системный curl действительно разобрал конфигурацию через stdin с `--version`:
это проверка синтаксиса без сетевого запроса, не подтверждение API на Windows.

Фактически прошли **96 тестов на Linux/Python 3.12 и 96 на Python 3.13** с
`-W error::ResourceWarning`. Также прошли compileall, CLI help и git diff --check.
Логи фактических запусков: `API_502_DIAGNOSTIC_TEST_RESULTS.txt`. Новая диагностика
не выполнялась с настоящим токеном на Windows в этой среде. Windows CI и две
реальные авторизованные HTTP-проверки требуют отдельного подтверждения.

SMA20/50, PAPER, LIVE и main не изменяются; торговые заявки не отправляются.
