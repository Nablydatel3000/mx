# Диагностика Invalid API JSON

Дата: 2026-11-05. База изменений: `e84246f`, ветка `gldrubf-v1-paper-api`, PR #1.

## Что известно о Windows-сбое

Пользователь сообщил, что на Windows прошли 68 тестов, после чего первый
`download_candles_windows.cmd` с диапазоном 2024-11-05 — 2026-11-06 (exclusive)
и интервалом day завершился `STOP: Invalid API JSON`.

Старая ошибка означала, что `json.loads`/декодирование выбросило исключение;
тот же общий обработчик мог ошибочно отнести Unicode-ошибку HTTP-запроса к JSON.
Ни метод, ни статус, ни тип ответа не сохранялись. Поэтому **установить реальный
сбойный метод по прежнему сообщению невозможно**. Нельзя объявлять причиной
неверный токен, прокси, календарь или отсутствие свечей без дополнительных данных.

Порядок вызовов в fetch без `--uid`:

1. `InstrumentsService/FindInstrument` — поиск GLDRUBF.
2. `InstrumentsService/FutureBy` — проверка фьючерса/UID.
3. `InstrumentsService/TradingSchedules` — официальный календарь, чанки по 7 дней.
4. `MarketDataService/GetCandles` — свечи, дневные чанки по 90 дней.

FindInstrument является первым возможным местом сбоя, но его фактический отказ
не подтверждён. Проверка временных границ fetch сейчас выполняется после discovery
инструмента. Даты сами по себе не объясняют JSON-ошибку: они не передаются в
FindInstrument/FutureBy. Правило `--to <= текущему времени UTC` сохранено; если
2026-11-06T00:00:00Z ещё не наступило, такой конец будет отклонён после discovery.

Хост исправлен на указанный в доступном официальном OpenAPI. Это подтверждённое

пробы обоих хостов из этой среды не получили HTTP-ответа API из-за сетевого/прокси
сбоя; токен и Authorization не отправлялись. Успешная доступность и авторизация
на машине пользователя должны быть проверены повторно.

## Исправления обработки HTTP

- Безопасная ошибка содержит только allowlisted метод, числовой HTTP-статус,
  нормализованный Content-Type и фиксированную категорию. Если HTTP-ответа нет,
  статус и Content-Type — unknown. Код CONNECT не выдаётся за HTTP-статус API.
- Произвольное значение Content-Type не выводится: только известный MIME-тип без
  параметров, missing или other. Токен, Authorization, URL прокси, тело ответа,
  серверное message/description и исходный текст сетевого исключения не выводятся.
- Разделены пустой ответ, неожиданный Content-Type, повреждённый JSON/кодировка,
  неверный корневой тип и error envelope внутри HTTP 200. Их нельзя принять
  за успешные данные. application/problem+json всегда является ошибкой.
- HTTP-ошибки классифицируются отдельно; их объекты закрываются без чтения тела.
  Обычные HTTP-ответы закрываются и при ошибке чтения.
- Обработаны IncompleteRead и прочие HTTPException: раньше они могли выйти
  за пределы безопасного обработчика. Unicode-ошибка запроса больше не называется
  ошибкой JSON.
- Ограничены три попытки по умолчанию, максимум пять; повторяются только временные
  сетевые/протокольные сбои, HTTP 408/429/5xx. Для плохого JSON, 401/403/407,
  redirect и ошибок проверки TLS автоматических повторов нет.
- Сохранены лимит тела 16 MiB, timeout 20 секунд, read-only allowlist, системная
  проверка TLS и запрет redirects. Переходов на другой хост с токеном, fallback
  на старый хост, отключения сертификатов и сохранения ответа для диагностики нет.
  Стандартная поддержка прокси urllib, включая настройки Windows, сохранена.

Пример **искусственной** диагностической строки, не результат реального запуска:

```text
STOP: API failure: method=InstrumentsService/FindInstrument http_status=200 content_type=text/html category=unexpected_content_type
```

## Проверки

До изменения фактически прошли исходные 68 тестов на Linux/Python 3.12.
Добавлены 14 тестовых методов, включая наборы подслучаев:

- REST URL, POST, Bearer, JSON и заголовки запроса;
- HTML, пустое/пробельное тело, повреждённый JSON, неверная кодировка, JSON null/list;
- HTTP 200 с code/message/error, problem+json, неверным или отсутствующим Content-Type;
- HTTP 302/400/401/403/407/408/429/500/502 и transport, возвращающий статус без HTTPError;
- DNS, proxy CONNECT, таймаут, TLS, reset, обрыв тела и ошибки HTTP-протокола;
- повторы временных ошибок, отсутствие повторов TLS, лимит размера и закрытие ответов;
- отсутствие утечек тестового секрета через тело, заголовки, URL, reason и traceback;
- для каждого из четырёх этапов реального fetch-пути: при имитированном сбое
  CLI показывает именно его метод и прекращает последующие вызовы/экспорт CSV.

**Результат:** 82 теста прошли на Linux/Python 3.12 и 82 на Python 3.13
с `-W error::ResourceWarning`. Логи: `API_HTTP_TEST_RESULTS.txt`.
compileall, CLI help и git diff --check также прошли.

Это offline-тесты с имитацией транспорта, а не подтверждение работы настоящего
API. Windows 68 PASS — сообщение пользователя о предыдущей версии; новые
82 теста на Windows здесь не выполнялись. Существующий CI запускает тот же набор
на Windows/Linux; его фактический результат нужно проверить в PR.

## Повторная проверка на Windows

1. Получить обновлённую ветку/ZIP PR #1 и снова запустить `setup_windows.cmd`.
2. Запустить `download_candles_windows.cmd` с read-only токеном через скрытый ввод
   или T_INVEST_TOKEN. Значение токена не отправлять в чат.
3. Использовать исторические границы, конец которых уже наступил в UTC.
4. Если появится STOP, передать только новую диагностическую строку с методом,
   статусом, Content-Type и категорией. Не включать токен, HTTP-дамп или тело ответа.

По этой строке можно будет установить сбойный метод. 401 относится к авторизации,
407 — к прокси-аутентификации, proxy_tunnel_error — к CONNECT до API. HTML при 200
указывает на неожиданный тип ответа, но сам по себе не устанавливает его источник.
TLS нужно исправлять через доверенные сертификаты/настройки сети, не отключением
проверки. Успех выгрузки и пригодность фактического календаря/свечей ещё предстоит
проверить на Windows с настоящим API.
