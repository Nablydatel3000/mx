# Отказ выбора текущего расписания GLDRUBF

> Отчёт до получения фактических кодов. Пользователь подтвердил расхождение
> регистра; выбор теперь использует ровно одно совпадение после casefold().
> [Актуальное исправление](EXCHANGE_CASEFOLD_RU.md). Ниже сохранён контекст прежней диагностики.

Дата: 17.11.2026. Ветка gldrubf-v1-paper-api, существующий PR #1.
База проверки: 6582ca69e52006b8e5ffaac4dd64ac9f60dfc766.

## Проверка → результат → ошибки → исправления → решение

**Проверка:** источник exchange, запрос/ответ TradingSchedules и выбор расписания
в api.py/current_sessions(). Реальный Windows-отказ предоставлен без кодов секций.

**Результат:** запрос соответствует protobuf/OpenAPI: POST
InstrumentsService/TradingSchedules, необязательная строка exchange, from/to UTC.
Ответ — объект с repeated-массивом exchanges; каждая запись содержит exchange и
days. Пропущенный exchanges в protobuf JSON означает пустой список, не ошибку
JSON и не разрешение торгов. Используемая структура exchanges[].exchange верна.

FindInstrument/InstrumentShort не содержит exchange. Код определяется через
FutureBy по найденному UID с проверкой ticker=GLDRUBF, RUB, lot=1. Берётся именно
Future.exchange (секция), не classCode и не realExchange (enum реальной биржи).
Оба календарных запроса используют сегодняшний UTC-день → +2 дня, не исторические
даты. Это в пределах документированного ограничения недели от текущего дня.

Официальные источники проверены повторно 17.11.2026: HEAD investAPI по-прежнему
3eaf23a25f598fe483c913184acdbd9132bc68d2, OpenAPI v1.43. Ссылки и SHA:
[реестр](CURRENT_SESSIONS_SPEC_REFERENCE.json).

- instruments.proto: TradingSchedulesRequest/Response, TradingSchedule,
  Future.exchange и InstrumentShort; OpenAPI повторяет эти определения.
- head-instruments.md: расписания прошлых дней недоступны; текущие расписания
  могут меняться и отличаются от реальной биржи, нужен также статус инструмента.
- markets.md различает FORTS (опционы) и FORTS_EVENING (фьючерсы). Упоминание
  общего расписания не доказывает взаимозаменяемость кодов для GLDRUBF.

**Обнаруженные ошибки:** прежний отказ объединял случаи нуля и нескольких точных
совпадений, не показывая ни запрошенную секцию, ни коды ответа. Повреждённые
структуры exchanges/days могли дать неточный технический отказ вместо явного
запрета календаря. Подтверждённой ошибки преобразования exchange не обнаружено.

**Исправления:** добавлены requested_exchange, returned_exchanges (уникальные
публичные коды), returned_count (число записей), exact_matches,
response_shape_valid; категории calendar_exchange_missing/ambiguous. Некорректные
списки/записи явно отклоняются. Общий конструктор запроса используется PAPER и
диагностикой, чтобы сравнение выполнялось на том же диапазоне.

Для вывода применяется документированный allowlist кодов. Произвольные строки,
включая отражённый токен, редактируются в other. Даже документированный код не
выводится, если содержит текущий токен. Запрос и сравнение используют исходное
значение без преобразования. Список кодов ограничен размером allowlist; тела,
дни/цены, Authorization, UID и дополнительные поля ответа не печатаются.
Unknown-коды сознательно не раскрываются целиком; их mapping этим не устанавливается.

**Решение:** при отсутствии единственного точного совпадения PAPER остаётся
заблокированным. Автоматический переход на FORTS, нормализация регистра,
выбор первой записи, объединение разных секций и обход контроля окон не добавлены.
SMA20/50, SQLite, расходы и механизм исполнения не изменены. main не меняется.

## Чего пока нельзя установить

Предоставленная строка доказывает только exact_matches != 1 в успешном ответе,
но не показывает, были ли это ноль или несколько записей. Нет фактического
FutureBy.exchange и кодов filtered/unfiltered ответов Windows. Поэтому нельзя
приписать отказ фильтру API, конкретному коду секции или особенностям GLDRUBF.
Авторизованные запросы здесь не выполнялись; токен у пользователя не запрашивался.

Безопасно выбрать расписание в рабочем режиме можно лишь при единственном
точном совпадении исходного FutureBy.exchange и корректных days, затем по-прежнему
проверить актуальный статус, реальные окна now/quote, свежесть и время сигнала.
Если такого совпадения нет, нужный mapping требует подтверждения API/поддержки
Т-Инвестиций, привязанного к GLDRUBF; общего названия MOEX недостаточно.

## Проверка Windows без исторических дат

1. Получить обновлённую ветку, выполнить setup_windows.cmd.
2. Запустить diagnose_current_sessions_windows.cmd. Он не запрашивает даты:
   используется тот же двухдневный диапазон current_sessions().
3. Ввести read-only токен скрыто в локальной консоли. Не присылать токен или raw.
4. Сохранить две безопасные JSON-строки current_filtered/current_unfiltered.
   Это результат диагностики, не разрешение запуска PAPER.

Вызовы: FindInstrument → FutureBy → один TradingSchedules с точным exchange →
один TradingSchedules без поля exchange. Каждая попытка одна, без retry. Оба
контрольных запроса используют один диапазон. Ни котировки, ни счёт, ни заявки,
ни виртуальное исполнение не запрашиваются. Диагностика ничего не сохраняет.
Первый запрос может завершиться API-ошибкой: второй всё равно выполняется;
выводятся только безопасные числовые коды/категория/статус, не текст ошибки.

| Результаты | Что подтверждается | Дальнейшее действие |
| --- | --- | --- |
| Filtered 0, unfiltered 1 exact | Расхождение двух ответов на одном диапазоне; возможно поведение фильтра или изменение API между вызовами | Повторить контроль и подтвердить причину; текущая версия не переключается на ответ без фильтра |
| Оба 0 exact | Код FutureBy отсутствует в обоих календарных ответах | Подтвердить соответствие у Т-Инвестиций; другой код не выбирать |
| Более 1 exact | Несколько записей одной секции | Не объединять и не выбирать произвольно, исследовать структуру у поставщика |
| Оба 1 exact | В текущей диагностике несоответствие кодов не воспроизвелось | Это ещё не проверка days/окон. Повторить обычный PAPER, который проверит их полностью |
| Invalid response / HTTP error | Нельзя достоверно оценить совпадение по этому ответу | Использовать безопасную категорию и числовые коды; не считать это отсутствием торгов |

Код выхода 0 означает только одно точное совпадение кодов в обоих ответах.
Успех второго запроса не превращает провал первого в успех. При новом запуске
обычный Forward теперь также покажет коды прямо в STOP и operations.log.
