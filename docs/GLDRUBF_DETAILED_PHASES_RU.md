# GLDRUBF: подробные торговые фазы и секундные границы

17.11.2026, gldrubf-v1-paper-api, PR #1. База: 42202badd1a90b91bd4fe822bff9872bcbabe327.

## Проверка и источник данных

Пользователь сообщил структуру девяти интервалов за 17, 18 и 19.11.2026 для
FORTS_FUTURES_WEEKEND. **Сами schedule.json/validation.json в этой рабочей копии
и вложениях текущего сообщения отсутствуют.** Нет их хешей и возможности
независимо сверить все legacy-поля/флаги/типы. Тесты reported_day() явно
реконструируют текстовое описание, с тестовым isTradingDay=True и только
сообщёнными legacy startTime/endTime. Это не импорт трёх реальных JSON-дней.
Для окончательной приёмки нужны оба исходных отредактированных файла.

Подтверждённая проблема прежнего кода: detailed span обязан был точно совпасть
с общим legacy-интервалом. Три последовательные регулярные фазы внутри
04:00–20:50 не удовлетворяли этому условию и блокировались.

## Официальные источники и предел подтверждения семантики

Изучен официальный RussianInvestments/investAPI HEAD
3eaf23a25f598fe483c913184acdbd9132bc68d2: instruments.proto/TradingDay,
TradingInterval и TimeInterval, сгенерированная instruments.md, common.proto /
SecurityTradingStatus и руководство markets.md. [Ссылки/SHA](GLDRUBF_PHASES_SPEC_REFERENCE.json).
Поиск по официальному репозиторию не нашёл нормативного списка точных названий
regular_trading_session_morning/main/evening или opening_auction_morning.
Type остаётся свободной строкой «название интервала», не enum.

Значит, нельзя объявлять новые имена универсальным официальным классификатором.
В этой PAPER-модели применена ограниченная явная таблица по сообщённым
наблюдениям пользователя. Разрешение регулярной фазы дополнительно требует
существующих проверок NORMAL_TRADING («нормальная торговля» в common.proto),
marketOrderAvailableFlag/apiTradeAvailableFlag, UID, свежей цены и текущего окна.
Один только type не разрешает исполнения. До LIVE нужны подтверждённая семантика
поставщика, полные файлы и отдельная приёмка реального исполнения.

| Типы из наблюдений | Решение PAPER | Источник/ограничение |
| --- | --- | --- |
| regular_trading_session, regular_trading_session_morning/main/evening | Кандидаты непрерывных окон | Названия и три конкретных span сообщены пользователем; разрешение условно текущему NORMAL_TRADING и остальным gates |
| opening_auction, opening_auction_morning | Никогда не разрешают сделку | Наблюдаемая открывающая фаза; официальные legacy-поля описывают аукцион открытия, не нормальную торговлю |
| clearing | Никогда не разрешает сделку | Наблюдаемая фаза клиринга, согласуется с назначением legacy clearingStartTime/EndTime |
| Любое другое имя, включая похожее на regular_trading_session_* | Обработка дня останавливается | Семантика недостаточно подтверждена; нет substring/case/эвристической классификации |

Таблица не распространяется на premarket, closing_auction, новые площадки или
новые имена type автоматически. Неизвестная фаза останавливает разбор дня и
вызывающий API/PAPER-цикл, а не молча исчезает из разрешённого расписания.
Это консервативное ограничение, включая неизвестную фазу будущего дня в ответе.

## Новые правила parse_day

- Торговому дню нужен непустой корректный intervals. Legacy-only fallback удалён.
  Неторговый день не получает окон даже при оставшихся interval records.
- Разрешённые кандидаты берутся исключительно из перечисленных regular types.
  Общий legacy span не превращается в окно исполнения.
- Точные повторы и generic/specific aliases одного span/семейства дают одну запись.
  Разные specific regular-session названия для одного span — противоречие.
- Частичные пересечения или вложенные неидентичные detailed spans блокируются,
  в том числе регулярной и аукционной/клиринговой фаз. Они не объединяются.
- Пропущенная фаза оставляет разрыв. Отсутствие повторной alias-записи не удваивает
  и не расширяет окно оставшейся подтверждённой фазы. Нет требования ровно девяти
  записей: этот count — наблюдение, не алгоритмическое правило.
- Legacy start/end, evening и premarket пары проверяются как внешние границы,
  а не создают разрешение сами. Regular span должен помещаться в такую пару.
  Если есть отдельная evening-пара, specific evening проверяется и против неё.
  Подробные auction/clearing сверяются с соответствующими legacy-исключениями,
  когда те присутствуют. Неполные пары/неположительная длина блокируются.
- Legacy auction/clearing остаются дополнительными исключениями: могут только
  уменьшить detailed regular окна. Они не создают промежутки торговли.
- Время окончания дня сохраняет прежнюю консервативную legacy-модель: не
  сокращается до последнего разрешённого тика при удалении исключений. Окончание
  trailing clearing 21:30 не переносит close с 20:50 на 21:30.

Для описанного дня получаются ровно три окна UTC:

```text
[04:00:00, 05:59:59)
[06:00:00, 15:59:59)
[16:00:00, 20:50:00)
```

## Включение конца и точность

TradingDay.contains сохраняет **a <= timestamp < b**. Начало включено, точный
конец исключён. End=05:59:59 не превращается в 06:00:00 и не увеличивается на
секунду. Поэтому 05:59:59 и 05:59:59.999999 запрещены; 06:00:00 разрешено новым
фактическим интервалом. Аналогично gap 15:59:59–16:00:00 не заполняется.
20:50:00 исключено, 20:50:01–21:30 — клиринг, не новое окно.

Контракт не формализует включённость конечной секунды для каждого type. Выбрана
сохранённая консервативная семантика, которая может отбрасывать реально доступную
конечную секунду, но не расширяет торговое время. Это нужно проверить по полному
снимку/поставщику перед изменением правила, без автоматического +1 second.
Границы с ненулевыми субмикросекундами отвергаются: datetime не может представить
их точно. Нулевые лишние разряды допустимы. Диагностический сборщик по-прежнему
умеет сохранить исходные наносекунды для анализа.

## Тесты и неизменённые части

Добавлены 12 методов: девять записей/три окна на всех трёх датах, 60 проверок
секундных/микросекундных границ, отсутствующие intervals/фазы/aliases, повторы и
порядок, неизвестные типы, перекрытия/противоречия, legacy-пары, precision,
casefold выбора секции с тремя labels и неторговый день. Всё это тестовые
реконструкции с явно обозначенным происхождением, не заявленные реальные снимки.

Старые положительные API fixtures были legacy-only. Они обновлены явными
regular detailed records тех же синтетических сессий: иначе новые требования
справедливо блокировали бы их. Старый тест, разрешавший unknown type при точном
совпадении с legacy, теперь требует отказа даже при таком совпадении.
Остальные сценарии клиринга/аукциона/ночных окон и торговых guards сохранены.

200 тестов прошли на Linux/Python 3.12 и 3.13 с ResourceWarning как ошибкой;
compileall/CLI help/diff-check PASS. [Фактический журнал](GLDRUBF_PHASES_TEST_RESULTS.txt).
SMA20/50, настройки стратегии, PAPER-движок, расходы, SQLite, обработка свечей,
статус/свежесть/запрет будущего и casefold выбора секции не изменены.

## Ограничения перед Windows PAPER

Новый авторизованный запрос и Windows PAPER здесь не выполнялись, успешный запуск
не заявляется. Сначала передать schedule.json и validation.json, чтобы независимо
проверить все legacy-пары, типы и границы именно трёх реальных дней. Нужны также
реальные статусы и котировки в нормальной сессии, в промежутках, у границ и на
клиринге. При конфликте parser по-прежнему останавливается; не сбрасывать SQLite
и не отключать guards. Возможные новые типы требуют отдельного подтверждения.
Реальные заявки, LIVE, merge и deployment не выполняются.
