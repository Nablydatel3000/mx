# GLDRUBF v1.0: история, replay, Forward PAPER

> Исторический отчёт предыдущей реализации. По умолчанию Forward PAPER теперь
> использует автоматические наблюдения `isComplete` без ручной evidence:
> [актуальный архитектурный аудит](AUTONOMOUS_FORWARD_AUDIT_RU.md).
> Описанные ниже требования evidence действуют для historical replay и явно
> выбранного legacy verified Forward. Старые базы и часы расчёта не мигрируются.

Дата: 2026-11-11. База изменений: c7b87ba. Ветка gldrubf-v1-paper-api, PR #1.

## Что изменено

Прежняя day-выгрузка и PAPER-прогрев зависели от исторического TradingSchedules,
который не предоставляет прошлых расписаний. Загрузка теперь архивирует
GetCandles напрямую. Historical replay и Forward PAPER отделены; оба используют
существующие strategy.py и engine.py. SMA20/50, контрактность и расчёт кросса не
переписаны. Оптимизация, реальные заявки, Sandbox-торговля и deployment отсутствуют.

## Архив истории

`fetch --interval day` / download_candles_windows.cmd разрешают прошлые даты.
FindInstrument/FutureBy проверяют GLDRUBF, UID, RUB и lot=1; GetCandles вызывается
с instrumentId=UID, CANDLE_INTERVAL_DAY, CANDLE_SOURCE_EXCHANGE, без optional limit,
чанками 90 дней. Старый календарь не запрашивается.
Удаление limit описано в [исправлении 30220](GETCANDLES_30220_RU.md).

API-клиент проверяет цены/OHLC, время и диапазон, завершённость, объём, источник,
конфликты дублей и UID, если он присутствует в записи. Пустой protobuf-список
может быть опущен; это пустой ответ, а не доказательство отсутствия торгов.
Архиватор дополнительно проверяет порядок исходных записей, уникальность дневных
UTC-label, отсутствие будущих timestamps, монотонность времени получения.

Успешные JSON-ответы сохраняются побайтно в raw. Исходный JSON не заменяется
нормализованным; запросы без Authorization и SHA-256 записаны в manifest.json.
HTTP-ошибки/не-JSON ответы не архивируются как рыночные данные. Секреты из
ошибочных ответов не пишутся в файлы. Ошибка записи raw не вызывает повторный
HTTP-запрос под видом сетевого сбоя.

Отдельно сохраняются candles.json/CSV, instrument.json, validation.json и
evidence_template.json. Цены нормализованы в десятичные строки API-пунктов, не
объявлены рублёвой ценой контракта. Текущий tick — метаданные сегодняшнего
инструмента, а не историческая денежная спецификация.

Папка должна быть новой/пустой. Файлы открываются для исключительного создания;
исходники/предыдущие снимки не перезаписываются. Даже неудачная валидация оставляет
полученные raw и отдельный статус failed; неподтверждённый снимок не допускается
к исполнению. При загрузке проверяются хеши raw/нормализации и согласованность
manifest с validation.json.

Опция `--compare` / вопрос Windows launcher сравнивают с предыдущим снимком того
же UID. Изменение или исчезновение завершённой свечи даёт blocked_revision,
новый и прежний источники сохраняются. Изменение незавершённой свечи и переход
в complete фиксируются отдельно. Сравнение не включает observed_at в экономическую
идентичность свечи. Его область — пересечение диапазонов; отчёт показывает,
полностью ли покрыт предыдущий запрос. При первом получении сравнения нет.

Промежутки между UTC-label называются unobserved_calendar_dates. Никаких
искусственных свечей, выходных или автоматических торговых дат не создаётся.
coverage_confirmed и trading_dates_verified в отчёте архива остаются false.
Отсутствие свечи/первая возвращённая дата не заменяют доказательство листинга,
полноты торгов или отсутствия торгов.

## Торговые даты и время знания

В проверенном контракте HistoricCandle есть time UTC и is_complete; эти поля
не задают исторические completed_at и available_at. DAY-запрос игнорирует часть
времени суток, но это не доказывает универсальное соответствие UTC-date торговой
дате GLDRUBF через ночные/специальные сессии.

Автоматическое соответствие GLDRUBF с настоящим API в этой среде **не установлено**.
Поэтому provider_day явно помечен как UTC-label, а для исполнения требуется
отдельная evidence. В тесте проверено, что явная торговая дата может отличаться
от UTC-label и не заменяется ею незаметно.

Шаблон содержит uid, snapshot_sha256 и по строке на каждую завершённую свечу:

| Поле | Смысл |
| --- | --- |
| time, candle_sha256 | Привязка к конкретной исходной свече; хеш уже заполнен |
| trade_day | Подтверждённая торговая дата или явно объявленное допущение replay |
| completed_at | Время завершения, строго после time, не позже получения complete |
| available_at | Время доступности сигнала, не раньше completed_at |
| kind | historical_assumption или verified; по умолчанию unresolved |
| source | Несекретная ссылка/описание основания; поле не является автоматической сертификацией |

Ряды должны быть уникальными, строго упорядоченными по торговым датам и времени
завершения; available_at не убывает. Требуется минимум 51 complete-свеча. Пустые
поля/незавершённые свечи не становятся сигналами. Будущие данные отклоняются.

Для заполнения нужно скопировать шаблон в отдельную папку inputs, не менять raw
или candles.json. Evidence/quotes размещаются вне папки результатов. CLI запрещает
использовать исходный снимок как каталог результатов/базу и перезаписывать входные
файлы экспортом. Новый снимок Forward хранится в output/history отдельно от ledger.

## Historical replay

Команда historical-replay / historical_replay_windows.cmd принимают архив,
evidence и независимые котировки time,price. В evidence нужны quote_uid,
quotes_sha256, quote_source и execution_windows. Окна — явные допустимые интервалы
модели, а не скрытый календарь по будням. При historical_assumption результат
прямо помечается как зависящий от допущений и с неподтверждённым покрытием.

Котировки не генерируются из closes. Хеш CSV можно получить локально в PowerShell:

```powershell
(Get-FileHash 'quotes.csv' -Algorithm SHA256).Hash.ToLowerInvariant()
```

Бар поступает в прежний движок в available_at, не в предполагаемое время
доступности из полного будущего массива. Стратегия видит только накопленный
префикс. Котировка с тем же timestamp не исполняет pending; требуется строго
более поздняя. Результат сохраняет расходы и хеши в research.json и SQLite.
Отклонение цены на величину slippage применяется против позиции, обе стороны
разворота оплачиваются. Дневной funding также является объявленной моделью,
особенно когда completed_at — допущение.

Старый calendar-replay сохранён для уже подтверждённых daily.csv/calendar.json.
Legacy signals остаётся математическим расчётом по day,close, не доказательством
доступности исторических данных и не источником допуска Forward.

## Forward PAPER

Команда paper / run_paper_windows.cmd требуют --history и --evidence.
До API проверяется kind=verified и структурная согласованность исходного снимка.
Нужны coverage_source, expected_trade_days и coverage_through: перечень ожидаемых
завершённых торговых дат должен точно совпасть со свечами, а покрытие должно
включать как минимум вчерашний день, не заявляя будущее. Это внешнее подтверждение
периода, **не вывод из отсутствующих свечей**.

Слово verified не делает файл подлинным. Владелец данных/аудитор должен проверить
источник торговых дат, окончания сессий и отсутствующих дат. Код проверяет
согласованность, хеши и неизменность ранее принятых подтверждений; достоверность
самостоятельно сочинённого источника установить невозможно. Без реального
основания такой файл создавать нельзя; unresolved блокирует работу.

Каждый цикл повторно получает историю от исходной границы, сохраняет новый
снимок и сравнивает все ранее завершённые свечи. Затем проверяются текущие UID,
tick/стоимость пункта, только **сегодняшний** TradingSchedules, GetTradingStatus
и свежая цена GetLastPrices. Оба времени — котировки и текущего наблюдения —
должны находиться в проверенном окне. Текущий завершённый торговый день не может
исчезнуть/остаться неподтверждённым после официального close.

Исторические сигналы после простоя не исполняются задним числом. Batch становится
известным сейчас; более поздняя наблюдаемая котировка может исполнить последний
pending. Новая completed-свеча без строки проверенного соответствия, ревизия,
устаревшее покрытие или противоречие расписанию блокируют цикл. Нужен процесс
подтверждения новых дней; полностью автономное пополнение evidence не реализовано.

Перед передачей котировки движку сохраняется forward_checks/*.json с проверенными
окнами/текущим временем, ценой, хешами снимка/evidence, затратами и версией
Python/SQLite/исходников. MARKET_GATES_PASSED подтверждает рыночные проверки,
но не саму сделку: движок отдельно проверяет строгое время сигнала и идемпотентность.
Ошибка записи проверки блокирует новое исполнение. Факт fills остаётся в SQLite.
Historical replay также записывает версии/хеши исходников в research.json.

Интервал опроса минимум 60 секунд, по умолчанию 60. Перезапуски с тем же UID,
настройками, данными и evidence не дублируют исполнения. Подтверждения могут
дополняться новыми днями, но старые строки/происхождение не переписываются.

## SQLite и ограничения финансовой модели

Основной engine.py не переписан: транзакции, recovery, funding и контроль
−1/0/+1 сохранены. Дополнительные workflow_context/timing_evidence закрепляют
режим и входные допущения. База одного режима не используется другим; старую
непомеченную базу с данными нельзя молча принять. Все исходные базы сохраняются.

Повторный historical-replay с теми же файлами идемпотентен. Изменённые сценарии
требуют отдельной базы. SQLite — авторитетный ledger; CSV — восстанавливаемый
экспорт. Никакого закрытия позиции перед разрывом по последнему close нет.

Комиссия/проскальзывание/funding — явные параметры, не подтверждённые тарифы.
Нет моделирования ГО, принудительных ликвидаций, стакана, очереди и полного
variation margin. LastPrices не равен исполнимому Bid/Ask. Финансовые результаты
такой модели не доказывают реальную исполнимость или преимущество SMA20/50.

## Официальная интеграция

Запрошены четыре страницы developer.tbank.ru (intro, protocols, token, sandbox).
Из этой среды они недоступны через сеть. Вместо выдумывания содержания проверен
официальный RussianInvestments/investAPI, HEAD
3eaf23a25f598fe483c913184acdbd9132bc68d2. Пути, хеши, URL и результат доступа
зафиксированы в HISTORY_PAPER_SPEC_REFERENCE.json.

REST реализует JSON-шлюз gRPC-контрактов: POST, Bearer, production endpoint из
OpenAPI. Для day оставлен консервативный chunk 90 дней при документированном
максимуме до 6 лет/limit 2400. Общая рекомендация — до 50 запросов/сек с IP;
сервисные лимиты в проверенной документации: instruments 200/мин, market data
600/мин. Они общие для методов/токенов, не бюджет каждого экземпляра. Сохранены
ограниченные повторы 429/5xx и сетевых ошибок, timeout, TLS и запрет redirects.

Read-only токен нужен даже для чтения рынка; он не запрашивается в Codex.
PAPER — локальный ledger, не Sandbox. Sandbox — отдельный тестовый контур со
своей авторизацией и особенностями исполнения; этот код его методы не вызывает.
LIVE отсутствует. Нельзя подменять production токен Sandbox-токеном или включать
broker orders для диагностики.

## Что проверить на Windows и настоящем API

| Вопрос | Состояние |
| --- | --- |
| Загружать raw day-историю? | Путь реализован без исторического календаря; реальную новую Windows-выгрузку ещё нужно подтвердить |
| Можно ли исследовать replay? | Да, на собственных данных с явными допущениями/источниками, привязанными хешами |
| Запускать Forward сразу после скачивания? | Нет: шаблон unresolved; нужны проверенные торговые даты/завершение/покрытие и реальные текущие статусы/окна |
| Доказана ли совместимость GLDRUBF с текущими date-label? | Нет, требуется сверка действительных свечей с источником торговых дат/сессий |
| Можно ли назвать систему автономной? | Нет, верификация новых дней и реального API остаётся внешним условием |

Для приёмки нужны реальный read-only download, анализ raw/validation, сверка
UID/date-label/isComplete и границ сессий GLDRUBF, независимые котировки,
проверенные исторические временные источники и затраты, затем контролируемый
Forward с восстановлением после перерыва. Токены/HTTP-дампы присылать не нужно.

Тесты используют только искусственные данные и имитацию транспорта. Журнал:
HISTORY_PAPER_TEST_RESULTS.txt. Реальный API с токеном, Windows launchers,
Sandbox и deployment здесь не запускались; Windows CI отдельно требует подтверждения.

## Фактически выполненные проверки

134 теста прошли на Linux/Python 3.12; те же 134 прошли на Python 3.13 с
`-W error::ResourceWarning`. В набор входят прежние 110 проверок и 24 новых
метода для архивов/переходов режима/Windows helper. Старые проверки, предполагавшие
запрет raw day-архива, изменены на утверждение прямого GetCandles без календаря.
Ни одна защитная проверка не отключена для получения зелёного результата.

Новые сценарии: точные raw-байты/хеши, пустой protobuf, пропуски без заполнения,
дубликаты внутри/между чанками, конфликт/ревизия/исчезновение complete,
переход incomplete → complete, неверные UID/OHLC/даты/порядок/flags, защита
входных файлов, невключение секретов HTTP-ошибки в архив, отказ записи без
сетевого повтора, явная смена UTC-label на торговую дату, causal replay,
строго следующая цена, SQLite restart без дублей, запрет смены режима/старых
подтверждений, future availability/coverage, текущий календарь/статусы,
блокировка после close/при неизвестном дне, сохранение gate перед исполнением
и отказ сделки при ошибке аудита. CLI обоих режимов проверен с имитацией API.

Прошли compileall, CLI help трёх entry points, git diff --check и проверка CRLF
всех .cmd. Побайтно подтверждено, что strategy.py и engine.py совпадают с базой
c7b87ba; их SHA-256 записаны в SPEC_REFERENCE. Python-зависимости не добавлялись.
