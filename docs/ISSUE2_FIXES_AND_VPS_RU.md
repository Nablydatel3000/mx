## Bootstrap, совместимость и сомнительные данные

Схема `user_version=1` хранит границу первого прогрева атомарно с bars/funding/pending.
Первый пакет может содержать меньше 51 свечи: он сохраняется для прогрева без сделок;
новая 51-я завершённая свеча уже может подтвердить пересечение. Незавершённые свечи
в SMA не входят. История обновляется и сверяется с ранее принятой, исчезновения,
изменения и вставки внутрь уже обработанной истории продолжают останавливать цикл.

Обычный перезапуск **новой версии** восстанавливает позицию и pending, исполняет
только после времени знания сигнала и не повторяет зафиксированный fill.
Старый формат без bootstrap-происхождения мигрируется консервативно: уже открытая
позиция сохраняется. Если есть pending, значения сохраняются, но включается
`migration_review_required`: доказать, что он не возник при историческом прогреве,
невозможно. До нового подтверждённого пересечения — `WAIT_MIGRATION_REVIEW`.
Новый реальный crossover заменяет старый pending и снимает эту блокировку.
Это явное ограничение совместимости; нельзя одновременно гарантировать исполнение
любого старого pending и запрет исторического bootstrap при отсутствии происхождения.
Старый исполненный исторический fill не стирается задним числом.

Порог возраста свечи не утверждён пользователем, поэтому production-default нет.
Возраст измеряется от UTC-метки поставщика, **не** от времени HTTP-ответа или
неизвестного клиринга. Время первого получения `isComplete` — время знания данных.
MSK отображается отдельно, UTC-выходные не удаляются. Соответствие DAY-метки точной
торговой сессии и полное покрытие истории по-прежнему не доказаны. Пропуски
календарных дней сами по себе не доказывают ни отсутствие торгов, ни потерю свечи.
Порог — проверяемая эксплуатационная политика, не восстановленный исторический календарь.

## Linux VPS

[Готовые файлы и инструкция](../deploy/linux/README_RU.md), конфигурационный мастер
`vps_setup.py` и команды `vps run/check/backup/restore/validate-config`:

- systemd запускает после сети/синхронизации времени, восстанавливает процесс после
  сбоя с ограничением частоты; SIGTERM корректно завершает работу. Код 78 для
  повреждённых данных/конфигурации/SQLite запрещает автоматические рестарты.
- SQLite постоянно хранится в `/var/lib/gldrubf`, raw/CSV/logs — `/var/log/gldrubf`.
  Маркер инициализации запрещает незаметное создание пустой базы после потери старой.
  Файл базы нельзя заменять/удалять при активном runner. NFS не поддерживается.
- Секреты root-only `0600`, `LoadCredential`, отдельный непривилегированный пользователь,
  TLS и запрет redirect сохранены. Токен не в argv/Git; в процессе он доступен только
  в памяти/окружении клиента. Настоящие токены здесь не вводились.
- Health timer независим от основного процесса. Проверяет PID + Linux start ticks,
  heartbeat, свежесть завершённых данных и время последней успешной итерации.
  Отсутствие первой успешной итерации не выдаётся за здоровье. Есть дисковый резерв.
- Telegram/HTTPS webhook выбирается локально, отдельные credentials. Durable outbox,
  повтор доставки и уведомление о восстановлении. Возможна повторная доставка
  после неопределённого сетевого исхода. Реальный канал здесь не проверялся.
- `operations.log`: 5 MiB + 5 копий. Retention raw/checks задаётся пользователем,
  последние два и последние два валидных снимка защищены от удаления. CSV — экспорт;
  не полная резервная копия. Лимиты journald задаёт ОС.
- Ежедневный SQLite online backup, quick_check и семантическая проверка рабочей копии,
  удержание последних 7 копий по умолчанию. Restore блокируется активным runner,
  проверяет расходы/состояние и сохраняет inode базы.
- Восстановление **старой** копии не может доказать отсутствие потерянных последних
  fills. По умолчанию restore ставит паузу для сверки. `--authoritative-ledger` требует
  явного подтверждения полного актуального журнала после корректной остановки/сверки;
  это не автоматическое разрешение запускаться со старой копии. При потере части
  журнала нельзя обещать отсутствие повторов. Автоматического отката базы нет.

Инсталлятор подготовлен и синтаксически проверен; в этой работе не запускался.
Службы не устанавливались, не включались и не стартовали. При полном падении VPS
его собственный monitor не может отправить уведомление: нужен внешний контроль
сервера и отдельное хранение копий. Это ограничение, не реализованный внешний сервис.

## Решение и оставшаяся приёмка

Подтверждённые дефекты закрыты воспроизводимыми offline-регрессиями. Код и файлы
для пользовательского VPS smoke подготовлены. **Успешная автономная работа с реальным
API на Windows/VPS пока не подтверждена**, и прибыльность не оценивалась.

Перед стартом надо локально задать возраст завершённой свечи, прежние расходы и
канал уведомлений; при переносе — полную остановленную базу. Затем проверить
настоящий read-only API, текущее расписание/статусы, часы, свежесть истории,
доставку уведомлений, плановый рестарт и backup. Не создавать искусственный сигнал
ради smoke; flat до нового crossover — ожидаемо. Реальные DAY CSV/SQLite пользователя
не предоставлены, фактический прежний исторический fill заново не вычислялся.
Официальные тарифы, funding, ГО, bid/ask и исполнимость LastPrices не подтверждены
этой доработкой. Для LIVE потребуются отдельное разрешение, проектирование и аудит;
в этом коде LIVE отсутствует.
