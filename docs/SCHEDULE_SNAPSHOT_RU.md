# Комплексная диагностика TradingSchedules GLDRUBF

> Этот отчёт описывает изолированный диагностический этап. После получения
> текстового описания фаз добавлена новая обработка parse_day:
> [правила и ограничения](GLDRUBF_DETAILED_PHASES_RU.md).
> Сборщик снимка по-прежнему не вызывает парсер и не разрешает PAPER.

17.11.2026, ветка gldrubf-v1-paper-api, PR #1. База: 7792cec8d74fb8f3b4bf0ae532ae0775222655ed.

Последний реальный Windows STOP: `Unrecognized detailed trading interval;
calendar mapping needs review`. Серия изменений исполнения приостановлена.
**parse_day(), стратегия, PAPER, SQLite и торговые ограничения не меняются.**
Новый модуль только собирает и проверяет локальные диагностические данные.
Без реального снимка ошибка интервалов не объявляется исправленной.

## Как получить и передать снимок

1. Получить обновлённую ветку целиком, при необходимости выполнить setup_windows.cmd.
2. Остановить прежний PAPER. Запустить **diagnose_schedule_snapshot_windows.cmd**.
3. Ввести read-only токен скрыто в локальной консоли. Даты не запрашиваются.
4. В консоли появится новая папка `data/schedule_diagnostics/<UTC-время>/`.
   В ней только **schedule.json** и **validation.json**. Исходный API-ответ
   отдельно не сохраняется. Папка data уже исключена из Git.
5. Перед передачей можно повторно проверить файл без токена и сети:

```bat
.venv\Scripts\python.exe -m src.gldrubf_bot.diagnose_schedule_snapshot --validate "data\schedule_diagnostics\<UTC-время>\schedule.json"
```

6. Прикрепить **оба JSON-файла** к следующему сообщению. Не присылать токен,
   переменные окружения, SQLite, старые raw-ответы или скриншот всей консоли.
   Для дополнительной ручной проверки в schedule.json должны быть только поля
   из схемы ниже, а в validation.json — локальные результаты валидации.

Код выхода 0 означает valid_for_diagnostics, 1 — needs_review/invalid либо сбой.
Если JSON-файлы созданы, needs_review/invalid тоже полезны для анализа: границы
не исправляются автоматически. Если файлов нет — передать только безопасную
категорию консоли; не пытаться выгружать полный ответ или секреты.

## Получение и состав JSON

Последовательность: FindInstrument(query=GLDRUBF) → FutureBy по UID → один
TradingSchedules. Используется существующий read-only клиент, attempts=1,
без retry, счетов, котировок, свечей и заявок. Исходный FutureBy.exchange сохраняется
в запросе, выбирается ровно одна запись по casefold, без alias или смены секции.
Диапазон тот же, что у current_sessions: сегодняшняя UTC-полночь → +2 дня,
включая следующий label для ночных сессий, без прошлого расписания.

Полный whitelist schedule.json:

- requestedExchange, exchange: исходный код FutureBy и код выбранной записи;
- from, to: UTC-границы фактического запроса;
- days: все дни выбранной записи в исходном порядке. Каждый день содержит date,
  isTradingDay, intervals и все 13 полей таблицы ниже;
- intervals: исходный порядок и повторения элементов `{type, interval: {startTs, endTs}}`.

Ничего кроме этих полей API не переносится. Нет UID/FIGI/тикера/названия инструмента,
сведений о счёте, Authorization, HTTP-заголовков или message/description ошибки.
Токен проверяется на отражение в разрешённых полях; при обнаружении снимок не
создаётся. Коды ограничены безопасными идентификаторами, типы — печатными Unicode
названиями до 160 символов без enum или выдуманной грамматики названий. Пустой type
сохраняется с предупреждением. Управляющие символы, UUID в типе и чрезмерные
значения не сохраняются; остальные поля API не копируются.
Небезопасное содержимое не попадает в exception/консоль как исходный текст.

UTC timestamps нормализуются с сохранением до девяти знаков наносекунд.
Пропущенные timestamps/type/intervals сохраняются как null; отсутствующая граница
interval — null, а не придуманное время. Пропущенный isTradingDay также null,
с предупреждением о protobuf default false. Дни и интервалы не сортируются,
не объединяются и не достраиваются. Выходные UTC не удаляются.

Файлы создаются в новой папке, повторная запись существующей папки запрещена.
После записи schedule.json перечитывается и валидируется. Ошибка записи/чтения
не превращается в успешный снимок. Размер JSON ограничен 2 MiB, дни — 32,
интервалы — 512 на день; это пределы диагностики, не лимиты API или правила торгов.

## Официальная схема и семантика

17.11.2026 повторно получены официальный HEAD RussianInvestments/investAPI
3eaf23a25f598fe483c913184acdbd9132bc68d2, instruments.proto, OpenAPI, markets.md
и head-instruments.md. SHA/ссылки в [реестре источников](SCHEDULE_SNAPSHOT_SPEC_REFERENCE.json).

TradingDay содержит date, bool is_trading_day, legacy timestamps и repeated
TradingInterval intervals. TradingInterval состоит из **string type** («Название
интервала») и вложенного TimeInterval с Timestamp start_ts/end_ts. В OpenAPI это
type:string и interval:{startTs,endTs}. **Закрытого enum типов интервала нет.**
Пример OpenAPI с type="type" не является реальным названием торговой фазы.

| Legacy-поле | Значение комментария официального контракта |
| --- | --- |
| startTime / endTime | Начало / окончание торгов UTC |
| openingAuctionStartTime / openingAuctionEndTime | Начало / окончание аукциона открытия UTC |
| closingAuctionStartTime / closingAuctionEndTime | Начало / окончание аукциона закрытия UTC |
| eveningOpeningAuctionStartTime | Начало аукциона открытия вечерней сессии UTC |
| eveningStartTime / eveningEndTime | Начало / окончание вечерней сессии UTC |
| clearingStartTime / clearingEndTime | Начало / окончание основного клиринга UTC |
| premarketStartTime / premarketEndTime | Начало / окончание премаркета UTC |

date — метка даты, isTradingDay — признак торгового дня, а не текущий статус
инструмента или разрешение рыночного исполнения. Отсутствие repeated-поля в
protobuf JSON может означать пустой список; оно не доказывает полноту календаря.
Ночные интервалы могут пересекать границу UTC-даты: диагностика это сохраняет.

Проверенные определения **не устанавливают** полный перечень значений type,
их приоритет относительно legacy полей, соответствие каждому legacy span,
универсальные правила overlap и допустимость исполнения по каждому названию.
Из type нельзя автоматически вывести «торги разрешены» либо удалить этот интервал.
Документированные аукционы/клиринг/премаркет также не означают одинаковую
доступность операций через API. Для выбора действий нужны реальный снимок и
подтверждение семантики, а затем отдельное изменение парсера с тестами.

Официальное руководство разрешает расписание от текущего дня, не прошлое;
расписание секции брокера может отличаться от биржевого. Нынешняя ошибка
указывает, что parse_day не распознал detailed span как точное зеркало известных
legacy границ. Это защитный отказ. Пока нет снимка, нельзя объявить, какая именно
фаза GLDRUBF его вызвала, или считать детальный список лишним.

## Что проверяется

Проверка корректности: строгий whitelist полей при offline-проверке, типы bool/
строк/массивов, UTC timestamps и точность наносекунд, from < to, положительные
границы каждого известного pair и detailed interval. Некорректный текст/структура
не сохраняются; безопасные, но перевёрнутые границы сохраняются с status=invalid.

Проверка полноты: отсутствие даты, флага, type, границ, detailed intervals и
временных полей у торгового дня, повторные даты, немонотонный порядок. Пропуски
и дубли помечаются; данные остаются наблюдениями. Некоторые legacy поля могут
законно отсутствовать: все отсутствующие пары не объявляются ошибкой.
Связка начала вечернего аукциона и начала вечерней сессии проверяется только
как диагностический порядок, без создания разрешённого окна.

Не проверяются как установленные факты: покрытие всех торговых дат GLDRUBF,
соответствие type фазам исполнения, историческая применимость и current trading
status. Даже valid_for_diagnostics имеет coverage_confirmed=false,
interval_type_semantics_verified=false, execution_permission=false.
Проверка --validate не читает соседний validation.json как доверенный результат,
а пересчитывает проверки из самого schedule.json. Подписанной подлинностью API
этот отредактированный снимок не обладает.

## Выполненные тесты и дальнейшее решение

Восемь новых регрессионных тестов проверяют весь mocked HTTP-путь, whitelist и
секреты, неизвестные названия типов, наносекунды/UTC и ночные границы, missing/
перевёрнутые поля, дубли/порядок, неоднозначность секции, защиту от перезаписи,
offline CLI, скрытый ввод/восстановление окружения и CRLF Windows launcher.
188 тестов прошли на Linux/Python 3.12 и 3.13 с ResourceWarning как ошибкой,
compileall и diff-check. [Фактический журнал](SCHEDULE_SNAPSHOT_TEST_RESULTS.txt).
Все ранее существовавшие Python-модули побайтно сохранены.

Авторизованный API и новый Windows-запуск здесь не выполнялись. Реальных
schedule.json/validation.json пользователя пока нет. После их получения нужно
сопоставить каждый type и span с legacy полями и официальными фазами GLDRUBF;
до этого изменения parse_day и допуска PAPER не предлагаются как готовое решение.
main, merge, LIVE, реальные заявки и deployment не затрагиваются.
