# TradingSchedules HTTP 400: проверка параметров и ограничения истории

Этот отчёт описывает прежнюю поставку. [Новая архитектура истории/PAPER](HISTORY_PAPER_V1_RU.md)
получает raw day напрямую через GetCandles без прошлого календаря. Историческая
выгрузка теперь возможна; торговые даты и время исполнения по-прежнему требуют
отдельного подтверждения, а не предположений о выходных.

Дата: 2026-11-05. База: `db1109a`, ветка `gldrubf-v1-paper-api`, PR #1.

## Подтверждено

Пользователь получил FindInstrument HTTP 200, затем TradingSchedules HTTP 400 /
application/json. Это локализует отказ в календаре, но старая строка не содержит
числового кода API, фактического exchange и дат запроса.

Официальное [руководство по сервису инструментов](https://github.com/RussianInvestments/investAPI/blob/3eaf23a25f598fe483c913184acdbd9132bc68d2/src/docs/head-instruments.md#получить-расписание-торгов)
прямо указывает: **расписание доступно не более чем на неделю с текущего дня;
расписания в прошлом недоступны**. Это ограничение метода, а не GetCandles.
Код пытался получить прошлый календарь по семь дней за раз. Разбиение не делает
историю доступной. Подтверждена несовместимость исторического сценария с
документированными возможностями TradingSchedules.

Нельзя утверждать без новой Windows-проверки, что конкретный ответ пользователя
содержал именно api_code=30003: его тело раньше не исследовалось.

## Фактическое построение запроса до исправления

1. `FindInstrument(query=GLDRUBF)` разрешает UID; в официальном InstrumentShort
   **нет поля exchange**.
2. `FutureBy(idType=UID, id=<найденный UID>)` возвращает полную запись фьючерса.
   Программа берёт `exchange` именно оттуда, без переименования.
3. Начало истории ограничивается `max(запрошенное начало, first1dayCandleDate)`
   при наличии официальной даты листинга.
4. Первый `from` — UTC-полночь полученной даты; `to = min(from + 7 дней,
   запрошенный конец)`. Дальнейшие запросы идут семидневными порциями.
5. Даты передаются как RFC 3339 UTC с Z; exchange — строка секции брокера.

Например, при начале 2024-11-05 и отсутствии более поздней first1dayCandleDate
первый запрос будет from=2024-11-05T00:00:00Z, to=2024-11-12T00:00:00Z.
Это иллюстрация формулы, **не захваченный Windows-запрос**.

## Сопоставление с контрактами

Использован официальный RussianInvestments/investAPI, коммит
`3eaf23a25f598fe483c913184acdbd9132bc68d2`, OpenAPI v1.43.

- [TradingSchedulesRequest и ответ](https://github.com/RussianInvestments/investAPI/blob/3eaf23a25f598fe483c913184acdbd9132bc68d2/src/docs/contracts/instruments.proto):
  exchange — необязательная строка секции/календаря; отсутствие фильтра возвращает
  все доступные площадки; from/to — UTC Timestamp.
- [Режимы торгов](https://github.com/RussianInvestments/investAPI/blob/3eaf23a25f598fe483c913184acdbd9132bc68d2/src/docs/markets.md):
  есть, например, FORTS и FORTS_EVENING, причём их назначения различаются.
  MOEX — фондовый рынок; замена exchange фьючерса на MOEX или FORTS без
  подтверждения была бы ошибкой. **Реальное текущее exchange GLDRUBF здесь
  авторизованным запросом не установлено.** MOEX_FUT в старых тестах —
  искусственная fixture, не подтверждённая характеристика GLDRUBF.
- [Каталог ошибок](https://github.com/RussianInvestments/investAPI/blob/3eaf23a25f598fe483c913184acdbd9132bc68d2/src/docs/errors/api_errors.json):
  30003 — from раньше текущей даты; 30002 — превышение 14 дней;
  30001/30004 — отсутствующие from/to; 30061/30062 — недопустимые границы;
  50001 — биржа не найдена. Каталог общий: упоминание 14 дней не отменяет
  более строгого ограничения «неделя с текущего дня» в руководстве метода.
  Не переносим ограничения свечей/других методов на календарь.

## Исправления

- Исторический `fetch --interval day` теперь останавливается **до HTTP-запросов**
  с точным сообщением: TradingSchedules не даёт прошлые расписания, нужен
  подтверждённый архив календаря. Нового импорта архивного календаря в этой
  поставке нет; его источник и историческое соответствие нужно установить.
- Проверки некорректного/будущего диапазона и UTC-полуночи перенесены перед
  discovery инструмента. Текущий день остаётся допустимым при корректном конце.
- Исторический minute-export через GetCandles сохранён: ему календарь не
  синтезируется и не приписывается. Это не заменяет верифицированный day/replay.
- Общий конструктор первого семидневного запроса используется API и диагностикой,
  чтобы проверка показывала те же параметры. Значение exchange не меняется.
- APIError дополнен `grpc_code` и `api_code`. Только для JSON ошибок читается
  максимум 64 KiB + один байт контроля; большой, повреждённый или нечитаемый
  ответ оставляет коды unknown. Выводятся лишь gRPC 0–16 и код из 175 значений
  официального каталога. Текст message/description, тело, токен и Authorization
  не выводятся и не сохраняются. HTTP-ошибка остаётся ошибкой, ответ закрывается.
- Ошибки TradingSchedules безопасно показывают exchange/from/to: даты
  канонизируются в UTC, exchange отображается только из списка документированных
  публичных названий, иначе other. Это **только редактирование диагностики**:
  фактически отправляемое exchange не заменяется. Неизвестные коды также unknown.

SMA20/50, виртуальные исполнения/P&L, runner PAPER и LIVE не менялись. При этом
общий API-клиент теперь безопаснее описывает отказы. Существующий PAPER-прогрев
тоже зависит от истории календаря: его архитектура здесь намеренно не менялась;
это остаётся ограничением для отдельной задачи с подтверждённым архивом.

## Проверка на Windows

Запустить **`diagnose_trading_schedules_windows.cmd`** из обновлённой ветки после
setup. Ввести исходные даты выгрузки и read-only токен через скрытый ввод.
В штатном случае выполняется два discovery-вызова FindInstrument/FutureBy,
затем по одной попытке трёх запросов TradingSchedules, без retries:

1. `requested_first_chunk`: настоящий первый запрос диапазона с учётом листинга.
2. `current_day_control`: текущая UTC-дата → следующая UTC-дата, то же exchange.
3. `current_day_discovery`: тот же текущий диапазон, exchange не передаётся.

Выводятся только структурированные публичные параметры, статус, числовые коды
ошибки и присутствие **точного** exchange инструмента в ответе. Не выводятся
UID, полный ответ, список произвольных секций или секреты. Unknown exchange
показывается как other, но проверяется по точному исходному значению.
Никакой календарь/история не сохраняются. Успешные контрольные запросы не
превращают провал исторического запроса в успех: код выхода остаётся 1.

Если история вернёт 30003, а текущие запросы успешны и exact exchange найден,
это подтвердит отказ из-за исторической даты. Если exchange отсутствует или
контроль тоже ошибочен — нужны полученные коды, нельзя автоматически выбрать
другую секцию. Для продолжения достаточно безопасных строк диагностики;
токен и дамп ответа не присылать.

## Фактическая верификация

Добавлены 14 тестов: точные параметры/UTC/порция, происхождение exchange из
FutureBy, числовой allowlist, секреты в message/description/URL, размер и сбои
чтения тела, закрытие соединения, отказ исторической day-выгрузки до HTTP,
сохранение minute-выгрузки, 400 внутри HTTP 200, три диагностических запроса,
отказ от смены секции, скрытый токен и восстановление окружения, CRLF launcher.
Прежний тест четырёх этапов fetch теперь фиксирует часы на допустимом текущем
дне: проверки методов и остановки после ошибки сохранены.

**110 тестов прошли на Linux/Python 3.12 и 110 на Python 3.13** с
`-W error::ResourceWarning`. Также прошли compileall, CLI help и git diff --check;
сверено точное совпадение 175 разрешённых кодов с официальным каталогом.
Результаты и логи: `TRADING_SCHEDULES_TEST_RESULTS.txt`. Авторизованное API на
Windows в этой среде не запускалось; фактические параметры и код прежнего
Windows-отказа остаются неподтверждёнными до новой проверки.

**Решение:** не повторять исторические запросы календаря в надежде на другой
результат. Для достоверной исторической дневной выгрузки нужен подтверждённый
источник старых расписаний. Сегодняшние сессии, правила по будням и closes
нельзя использовать вместо них. main и merge не затрагиваются.
