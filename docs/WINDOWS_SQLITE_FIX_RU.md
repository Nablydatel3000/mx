# Исправление SQLite / WinError 32

Дата: 2026-11-05. Базовый коммит ветки `gldrubf-v1-paper-api`:
`47dc6394ba9178337dcc6564e08615c0528aad10`.

## Причина

`sqlite3.Connection` как контекстный менеджер завершает транзакцию, но **не
закрывает соединение**. Поэтому `with sqlite3.connect(...)` не гарантирует
освобождение дескриптора до удаления `TemporaryDirectory`. На Windows открытая
SQLite-база препятствует удалению; на Linux unlink обычно разрешён. Сборщик мусора
не является гарантией своевременного закрытия, особенно при исключениях и
сохранившихся traceback.

Пользователь сообщил о 62 тестах и 13 ошибках Windows, включая `legacy.db`.
Полный Windows traceback не предоставлен. До исправления исходные 62 теста здесь
прошли на Linux. Затем добавлен контроль ресурсов: он удерживает сильные ссылки
на реальные SQLite-соединения и перед cleanup проверяет, что они уже закрыты.
На неизменённом управлении соединениями этот контроль выявил **13 failures**.
Это обнаружение утечек на Linux, а не воспроизведение Windows WinError 32.

## Группы обнаруженных утечек

| Группа | Затронутые тесты с контролем ресурсов | Причина | Исправление |
| --- | ---: | --- | --- |
| `test_engine.EngineTests` | 2 | Прямые подключения для изменения состояния и установки fault-injection trigger оставались открыты | `closing(...)` с внутренним транзакционным контекстом |
| `FinancingChronologyAudit` | 8 | Подключения в `fund_row()` и при изменении funding/state для проверки recovery оставались открыты | Закрытие всех пяти мест прямого подключения, включая ранний return |
| `PaperTests` и legacy-сценарий `WorkflowTests` | 3 | `execute_paper()` не закрывал подключения после успешной записи, idempotent return и исключений | Внешний `closing(...)` вокруг транзакционного контекста в рабочем legacy-коде |

Названия всех 13 обнаруженных тестов и трассировки сохранены в
`WINDOWS_SQLITE_REGRESSIONS_BEFORE.txt`. Без полного исходного Windows-журнала нельзя
утверждать точное взаимно однозначное соответствие каждой из сообщённых ошибок.

## Изменения

- `execute_paper()` теперь использует
  `with closing(sqlite3.connect(...)) as db, db:`. Сначала выполняется commit или
  rollback, затем `close()` при любом выходе. Простая замена на один `closing`
  без транзакционного контекста была бы неверной: она могла бы потерять запись.
- Исправлены все семь прямых SQLite-контекстов в существующих тестах.
- Все четыре семейства тестов, работающие с SQLite и временными директориями,
  используют `SQLiteResourceTestCase`. Проверка не вызывает `gc.collect()`,
  не игнорирует ошибки удаления и не делает повторных попыток cleanup.
  Обнаруженные утечки закрываются после фиксации failure, чтобы не создавать
  каскад вторичных ошибок уборки.
- `PaperEngine.db()` уже имел commit/rollback и `finally: close()`; менять его
  не понадобилось. Новые тесты проверяют успешную транзакцию, rollback и отказ
  конструктора на legacy-базе без изменения её содержимого.
- Добавлены шесть регрессионных тестов: ранние возвраты/ошибки legacy;
  SQLite storage fault и rollback; транзакции основного движка; отказ конструктора;
  освобождение runner lock после исключения; повторный экспорт в каталог с
  кириллицей и пробелами. Проверяется возможность удаления файлов до уничтожения
  удерживаемых Python-объектов соединений.

SMA20/50, параметры стратегии, алгоритм исполнения и расчёт P&L не изменены.
Не добавлены LIVE, API-методы заявок или зависимости приложения.

## Дополнительная Windows-проверка

Проверены пути файлов, `TemporaryDirectory`, файловые контексты CSV/JSON,
замена экспортов через `os.replace`, runner lock и Windows launchers.
Экспорт закрывает файлы до замены; `runner_lock` закрывает файл и освобождает
блокировку в `finally`. Windows-ветка `msvcrt` будет проверена CI; её успешный
запуск на Linux не заявляется. `.cmd`-файлы не менялись, их CRLF сохранены.
Других подтверждённых Windows-дефектов по доступным исходникам не установлено.
Блокировка файлов сторонним приложением/антивирусом и права конкретного каталога
не исключаются и локально не воспроизводились; подавлять такие ошибки не стали.

## CI и существующий PR

Добавлен `.github/workflows/tests.yml`: `windows-latest` и `ubuntu-latest`, Python
3.11 / 3.12 / 3.14. Запускаются unit tests, compileall и CLI help без токенов
брокера. Триггеры: push в `gldrubf-v1-paper-api`, PR в `main`, ручной запуск;
права `contents: read`, никаких deployment или merge.

Существующий PR: https://github.com/Nablydatel3000/mx/pull/1. Его Git head до
изменений совпал с веткой. GitHub GraphQL и REST карточки PR возвращают `Forbidden`;
редактирование заголовка/описания через API не подтверждено. Коммит исправления
`34f8794` отправлен в существующую ветку PR; после push удалённые ссылки ветки и
`refs/pull/1/head` совпали с ним. Удалённый `main` остался на
`842b017477fc610955b75a3a7f37525c5e9f0c68`. Чтение Actions runs через API также
вернуло `Forbidden`, поэтому результаты CI получить не удалось.
Сохранение workflow и push сами по себе не доказывают выполнение Windows CI.
Перед приёмкой нужно проверить фактические
статусы Windows jobs в Actions/PR; при отсутствии запуска включить Actions и
запустить workflow. `main` не изменять, merge не выполнять.
