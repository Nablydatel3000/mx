# Диагностика снимка счёта без торговых заявок

**Продолжение 19.11.2026: причина отказа GetMarginAttributes установлена по
реальному коду 30051 — [MARGIN_30051_RU.md](MARGIN_30051_RU.md).**

18.11.2026. Изменения только read-only приёмки относительно `96cac6e`.
PAPER, стратегия, SQLite, торговый LIVE, его проверки/файлы и systemd не изменены.
На Jino Codex не подключался, токен не получал, новые реальные ответы не видел.

## Что установлено

Со слов пользователя: FULL_ACCESS, HTTP 200, 15 000 ₽ внесено, GO LONG 1035,82 ₽,
SHORT 1036,67 ₽, 1 ₽/пункт, комиссия заявки из двух контрактов 20,28 ₽,
GetMaxLots LONG 10 / SHORT 11, открытых заявок 0. Это не полный снимок обеспечения.

**Причину конкретного `account_snapshot` установить по этим значениям нельзя.**
Подтверждён дефект диагностики: все локальные ошибки скрывались за одной
категорией; `capital_long/short` автоматически добавлялись при отсутствии
валидного снимка, даже если никакого расчёта свободных рублей не было.
Следовательно, прежние capital-блокировки сами по себе не доказывают нехватку денег.

`fee_ceiling_long/short` имеют независимую подтверждённую причину: **20,28 > 20**.
Новый предлагаемый потолок — **25 ₽ за одну заявку из двух контрактов**:
запас 4,72 ₽ (23,27%) сверх этой оценки. Это предел отказа, не подтверждённый тариф
и не цена всего разворота; закрытие и открытие оцениваются отдельно.
При новой оценке выше 25 ₽ проверка продолжит блокировать. В расчёт капитала
попадает фактическая оценка брокера 20,28 ₽, а не искусственные 20 или 25 ₽.
Новый пример конфигурации использует 25 ₽; установленный конфиг сам не меняется.

## Условия отказа исходного Broker.account

Код `live_api.py` не изменён. Выполнен повторный GET официальных protobuf
`operations.proto` и `users.proto`, HTTP 200; хеши совпали с предыдущей проверкой:
[источники](CONTRACT_SOURCES.json). Сверены `PositionsResponse`,
`PortfolioResponse`, `WithdrawLimitsResponse`, `GetMarginAttributesResponse`.
Схема не означает, что конкретный REST-ответ уже проверен.

| Проверка | Что вызывает отказ |
|---|---|
| GetPositions/GetPortfolio | `accountId` отсутствует или отличается от запрошенного |
| GetPositions | `limitsLoadingInProgress=true`; неверные целочисленные balance/blocked; ненулевая чужая позиция securities/options/futures |
| Позиции | Повтор GLDRUBF; другая ненулевая невалютная позиция в портфеле; нецелая quantity или abs(quantity)>2; blocked вне 0..2; balance расходится с quantity при blocked=0 |
| GetMarginAttributes | Отсутствует/некорректен любой из liquidPortfolio, startingMargin, minimalMargin, correctedMargin, amountOfMissingFunds; валюта не RUB; неверные units/nano |
| Маржинальные инварианты | Отрицательные starting/minimal/correctedMargin либо startingMargin < minimalMargin |
| Денежные массивы | Некорректные записи/числа, повтор RUB, ненулевая другая валюта в money/blocked/blockedGuarantee |
| GetPortfolio | Отсутствует/не-RUB/некорректен totalAmountPortfolio; некорректные quantity, varMargin или expectedYield позиции |
| Любой метод | Ошибка HTTP/API/сети, неверный тип JSON/поля, отсутствующее обязательное поле |

Недостаток денег — отдельный случай: корректный, но малый/нулевой/отрицательный
остаток не превращается в ошибку схемы. `amountOfMissingFunds>0` или liquid меньше
маржинальных требований устанавливают `margin_deficit`; снимок остаётся валидным,
но капитал не допускается. Наличие ненулевого дефицита нельзя игнорировать.

Официальные repeated-поля могут отсутствовать: это пустые массивы, а не ошибка.
Пустые money дают 0 рублей, не внесённые пользователем 15 000 ₽. Пропущенные нулевые
units/nano в корректном MoneyValue допустимы; отсутствующий целиком обязательный
MoneyValue или неизвестная валюта не заменяются нулём.

## Исправление диагностики

Четыре ответа читаются один раз и остаются только в памяти. Проверяется форма
массивов и MoneyValue, затем **тот же исходный Broker.account** выполняется
на этих ответах без повторных HTTP. Дополнительные проверки отвергают null/неверный
тип массива и не-bool флаг загрузки, не разрешая их интерпретацию как пустой счёт.
В отчёт попадают только фиксированные имена полей, причины отказа, наличие/типы,
количества записей, нормализованные суммы RUB и булевы результаты сверки счёта.
Ни токен, ни ID счёта/инструментов/позиций, ни произвольный API body не сохраняются.
Неизвестная ошибка остаётся блокировкой, её текст не печатается.

При успешной валидации показываются все составляющие консервативного минимума:

1. GetPositions: money RUB − blocked RUB.
2. GetWithdrawLimits: money RUB − blocked RUB − blockedGuarantee RUB.
3. GetMarginAttributes: liquidPortfolio − startingMargin.
4. GetMarginAttributes: liquidPortfolio − correctedMargin.

Используется минимум этих четырёх значений. Сохранён прежний консервативный учёт
блокировок; семантика полей и возможное двойное ограничение не менялись предположениями.
Общая стоимость портфеля и лимит GetMaxLots не подставляются вместо свободных RUB.

В общем `report.json`: `statistics.account_diagnostic` содержит доказательства.
`failure_group` различает schema_error, account_state_invariant и endpoint_error.
Если снимок невалиден, capital_* остаются блокировками, но имеют
`evaluation=not_evaluated`, `reason=account_snapshot_unavailable`, без выдуманных
required/available. При валидном снимке — `evaluation=evaluated` и суммы расчёта.

### Условная проверка арифметики, не допуск реального счёта

При неизменных GO×3, резерве 2000 ₽, двух контрактах, сценарной просадке
2097,2 пункта на контракт, стоимости пункта 1 ₽ и оценке комиссии 20,28 ₽:

| Сторона | Требуемый капитал | Запас, только если API подтвердит 15 000 ₽ доступных |
|---|---:|---:|
| LONG | 2×1035,82×3 + 4194,40 + 2000 + 20,28 = **12 429,60 ₽** | 2570,40 ₽ |
| SHORT | 2×1036,67×3 + 4194,40 + 2000 + 20,28 = **12 434,70 ₽** | 2565,30 ₽ |

Учитывается min(доступный минимум, liquidPortfolio, 15 000). Дефицит блокирует
даже при достаточном числовом минимуме. Просадка сценарная, не гарантия риска.

## Обновление уже установленной приёмки на Jino

В SSH-терминале пользователя, из отдельного клона `mx-live-check`, созданного
для приёмки, **не из каталога работающего PAPER**:

```bash
cd ~/mx-live-check
git switch feature/gldrubf-live-gated
git pull --ff-only origin feature/gldrubf-live-gated
sudo python3 deploy/live/update_readonly.py
sudo gldrubf-live-check account-diagnostics
```

Если клон находится не в домашнем каталоге, используйте его фактический путь.
Не запускайте первичный install_readonly.sh повторно поверх существующей установки.

Обновитель не делает API-запросов. Под общей блокировкой read_only.lock заменяет
только live_acceptance.py, новый account_diagnostics.py и wrapper gldrubf-live-check.
Проверяет известную версию установленного кода и неизменность live_api.py;
при неизвестной версии, symlink или занятой блокировке отказывается от обновления.
Копии заменяемого кода сохраняет в отдельной root-only папке acceptance-code-*.
Конфиг, токен, журналы, состояние, SQLite и службы не читает/не меняет, кроме
открытия существующего read_only.lock для блокировки. Прерванное копирование
можно повторить: допускается смесь прежних и ожидаемых новых файлов, но не
произвольный локально изменённый код. При отказе не обходите проверку вручную.

Команда account-diagnostics выполняет **только четыре метода счёта**, никаких
торговых методов, и печатает безопасный JSON. Частный файл:
`/var/lib/gldrubf-live-acceptance/account_diagnostic.json`, права 0600.
Суммы счёта — личная информация; передавайте файл только для частного анализа.
Не передавайте токен, config.json, SQLite или снимок полного ответа API.
Для анализа нужны `failure`, `findings`, `methods`, `availability_components_rub`,
`snapshot`, `method_checks`; это всё уже в безопасном файле.

После локального принятия предлагаемого потолка комиссии, отдельным действием:

```bash
cd /opt/gldrubf-live-acceptance/mx
sudo python3 -m src.gldrubf_bot.live_acceptance fee-limit
sudo gldrubf-live-check
sudo gldrubf-live-status
```

fee-limit меняет **только acceptance** max_order_fee_rub с 20 на 25, сохраняя
другие значения, владельца и права. Для иной прежней суммы требует ручного
рассмотрения. Не меняет конфиг торгового LIVE и не выдаёт разрешения на торговлю.
Вспомогательная диагностика не затирает прежний полный report.json: его статус
будет явно «не соответствует последней попытке» до следующего полного check.

**Итог:** устранена непрозрачность отказа, проверки капитала сохранены.
Конкретная причина реального account_snapshot ждёт нового безопасного JSON.
Ни успешный тест на Jino, ни допуск LIVE этим изменением не заявляются.
