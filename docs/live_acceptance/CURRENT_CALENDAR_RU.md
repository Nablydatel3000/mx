# Отказ current_calendar и проверка границ IOC

19.11.2026. База `feature/gldrubf-live-gated` / `b3e1fc6`.

## Подтверждённое и неизвестное

Пользователь сообщил: проверки счёта и капитала успешны, остаток 15 100 ₽,
капитал робота ограничен 15 000 ₽, комиссия двух контрактов 19,97 ₽.
Единственный blocker — current_calendar / schema_or_validation_error,
хотя TradingSchedules вернул HTTP 200. Также book_within_proposed_limits=false.
Codex не подключался к Jino, токен и фактический JSON расписания не получал.

**Точное условие отказа реального расписания пока неизвестно.** HTTP 200
подтверждает транспорт, но не единственность секции, форму days, допустимость
типов и согласованность временных границ. Сообщения core-парсера раньше
скрывались общей категорией read-only отчёта — это подтверждённый дефект диагностики.
Нормальное отсутствие текущего времени внутри окна само по себе не вызывает
исключение parse_day/current_sessions: эти функции разбирают расписание.
Поэтому объяснять current_calendar только закрытым рынком нельзя.

## Минимальное исправление приёмки

parse_day, current_sessions, PAPER и торговый LIVE **не изменены**. Новый
market_diagnostics.py получает TradingSchedules один раз и вызывает тот же
current_sessions на ответе в памяти. Каждая запись дня отдельно проверяется
тем же parse_day, чтобы сохранить индекс проблемного дня и фиксированную причину:
unknown_detailed_phase, missing_detailed_intervals, detailed_legacy_contradiction,
overlapping_detailed_intervals, incomplete_legacy_pair, invalid_timestamp,
conflicting_day_records и другие. В полном check категория теперь
calendar_validation_error, поле reason — конкретное условие, а не произвольный
текст исключения/API. Неизвестная ошибка продолжает блокировать.

Безопасный JSON содержит только выбранные даты, флаги, legacy-поля, типы/границы
интервалов, результаты разбора, разрешённые окна и сравнение секций с casefold.
Небезопасные значения редактируются, IDs/токен/Authorization и полный
ответ не сохраняются. Смысл неизвестных фаз не угадывается. Некорректный будущий
день также не пропускается ради разрешения текущего дня.

### Время и обычное ожидание

- Запрос сохраняет исходный instrument.exchange, UTC from/to и прежнее окно
  от текущей UTC-полуночи на два дня. Никакой подстановки FORTS/MOEX.
- Все сравнения выполняются timezone-aware в UTC. Московская дата/UTC+3 выводится
  рядом для объяснения смены даты; timezone сервера не используется как биржевой.
  Дата метки API не объявляется доказанной торговой датой.
- Границы остаются **[start, end)**: начало включено, конец исключён. Например,
  конец 05:59:59 не округляется до 06:00:00. Пробелы не заполняются.
- Аукционы, клиринг и неизвестные фазы не получают разрешений.
- calendar_state=outside_confirmed_windows означает отсутствие попадания в
  подтверждённое окно, а не доказательство отсутствия торгов вообще. Отдельно
  показано has_current_utc_date_label; полное покрытие календаря не предполагается.
- Котировка, книга и момент оценки должны попасть в один непрерывный интервал.
  В market сохраняются remaining_session_seconds, session_buffer_ok, wait_reasons.
  Прежний запас **не меньше 60 секунд** до исключённого конца не менялся.
  Время 20:49:00 при end=20:50:00 проходит запас ровно 60, 20:49:01 уже нет.
- Ошибка схемы остаётся blocker. Валидное расписание вне окна или недостаточный
  остаток времени дают tradable_now=false без ложного schema_or_validation_error.

## IOC и book_within_proposed_limits

Сверена фактическая формула в live.py, без исполнения торговых команд:

`BUY limit = последняя биржевая цена + max_slippage_ticks × minPriceIncrement`

`SELL limit = последняя биржевая цена − max_slippage_ticks × minPriceIncrement`

Текущий предел **2 шага**, конфиг не изменён. Это граница от свежей последней
сделки, а не от midpoint или лучшей цены книги. При шаге 0,1 и last=100 получаем
BUY=100,2 / SELL=99,8. Для BUY требуется ask≤100,2, для SELL bid≥99,8.
Ask=100,3 означает отклонение 3 шага и корректный отказ LONG; повышать предел
ради прохождения проверки нельзя. Реальное значение last/bid/ask из сообщения
пользователя неизвестно, поэтому точную причину его book-флага пока не подтвердить.

В прежнем отчёте book_within_proposed_limits был AND обеих сторон; ядро же
проверяет сторону целевой заявки. Теперь отдельно показаны long_price_checks и
short_price_checks, лимиты и adverse_distance_ticks. Общий флаг по-прежнему
требует обе стороны; он не ослаблен. Добавлены отсутствовавшие в отчёте проверки
сетки цены и лимитов limitDown/limitUp, уже имеющиеся в ядре. Нет округления или
выдуманной цены. Старая котировка, пустая сторона книги, неверная сетка и выход
за биржевые лимиты не дают разрешения. Успех ценовой проверки одной стороны
не является торговым разрешением. IOC/FAK может исполниться частично либо
не исполниться; проверка лучшего уровня не гарантирует объём двух контрактов.

## Обновление на Jino и получение точной причины

В отдельном клоне приёмки, не в рабочем PAPER:

```bash
cd ~/mx-live-check
git pull --ff-only origin feature/gldrubf-live-gated
sudo python3 deploy/live/update_readonly.py
sudo gldrubf-live-check calendar-diagnostics
sudo gldrubf-live-check
sudo gldrubf-live-status --json
```

Первый диагностический запуск читает только FutureBy и TradingSchedules.
Он не запрашивает счета и не отправляет торговых поручений. Файл:
`/var/lib/gldrubf-live-acceptance/calendar_diagnostic.json`, права 0600.
В нём нужны failure, days с parse_ok/reason/legacy/intervals, exchange_summary,
UTC/MSK-время и диапазон запроса. Для цены нужны market.quote_price,
best_bid/best_ask, bounded_limit_*, long_price_checks/short_price_checks и
wait_reasons из полного report.json. Все эти поля уже доступны через status --json.
Передавайте безопасные отчёты только для частного анализа; токен, конфиг,
SQLite и полный ответ API не нужны.

Обновитель поддерживает известные предыдущие версии, сохраняет копии кода,
берёт общий read_only.lock и пропускает неизменённые файлы. Для базы b3e1fc6
добавляется market_diagnostics.py, обновляются live_acceptance.py и wrapper.
Конфиг, лимит проскальзывания, деньги/SQLite, токен, PAPER и systemd не меняются.
Вспомогательная диагностика не затирает полный report.json: до следующего check
status явно показывает, что старый полный отчёт не соответствует последней попытке.

**Следующее решение по core-парсеру — только после реального снимка.**
Если reason укажет на неизвестную фазу или противоречивые границы, сохраняется
блокировка до проверки семантики. Успешный read-only отчёт не включает LIVE.

## Проверки

**98 целевых тестов прошли на Linux/Python 3.12.14 и отдельно 3.13.5.**
Также прошли compileall, shell syntax, CLI help, diff check и обновление точной
версии b3e1fc6 во временном каталоге с повторным запуском. SHA256 подтвердили
неизменность ядра PAPER/LIVE. Windows, Jino и CI в этой сессии не проверены.

Тесты используют mocks и реконструкцию ранее сообщённых девяти интервалов за
17–19.11.2026, **не фактический JSON нового запуска на Jino**. Проверены смена
UTC/MSK-даты, timezone offsets, начало/исключённый конец с микросекундами,
зазоры, аукционы/клиринг, запас 60 секунд, разные фазы котировки/исполнения,
ошибки схемы/alias/пересечений/legacy, casefold, неизвестные фазы, неизменные
границы двух шагов и раздельная оценка LONG/SHORT. Результаты и команды:
[CURRENT_CALENDAR_TEST_RESULTS.txt](CURRENT_CALENDAR_TEST_RESULTS.txt).
Реальная повторная проверка остаётся за пользователем. Заявки, активация LIVE,
merge и deployment не выполнялись.
