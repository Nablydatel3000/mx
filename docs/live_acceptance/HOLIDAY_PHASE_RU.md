# 21 ноября: holiday_trading_session_morning

19.11.2026, ветка feature/gldrubf-live-gated, база 44e4261.

**Точная причина current_calendar установлена. Разрешающее исправление
парсера не внесено: подтверждения семантики недостаточно.**

## Установленные факты

По сообщению пользователя API возвращает секцию FORTS_FUTURES_WEEKEND,
корректно разбираемые 19/20 ноября и две записи 21 ноября с одинаковыми
07:00–16:00 UTC: holiday_trading_session_morning и regular_trading_session.
Полный оригинальный JSON 21 ноября не приложен. 07:00–16:00 UTC соответствует
10:00–19:00 MSK; это арифметика часовых поясов, не подтверждение торгового режима.

В api.py / parse_day проверка `kind not in regular|auctions|{'clearing'}`
останавливается на holiday_trading_session_morning до объединения интервалов.
Смена порядка записей не помогает. current_sessions проверяет все возвращённые
дни, поэтому неподтверждённая фаза 21 ноября блокирует весь ответ, в том числе
при проверке 19 ноября. Это не ошибка времени сервера и не обычный выход из окна.
Будущий день не отбрасывается для обхода защиты.

## Что дали официальные источники

Официальный репозиторий RussianInvestments/investAPI прочитан на коммите
3eaf23a25f598fe483c913184acdbd9132bc68d2; contracts/instruments.proto,
instruments.md, markets.md и faq_instruments.md получены HTTP 200.
[URL, хеши, цитаты и результаты поиска](HOLIDAY_PHASE_SOURCES.json).

- TradingInterval.type — строка «Название интервала», не закрытый enum.
  Отдельных определений holiday_trading_session_morning и его допустимых
  поручений в изученных документах нет. Поиск этой строки, holiday_trading_session
  и FORTS_FUTURES_WEEKEND по документации .md/.proto/.json дал 0 совпадений.
- TradingDay содержит UTC start/end и подробные интервалы. Схема не утверждает,
  что совпадающие записи с разными type обязательно являются синонимами.
- markets.md приводит 10:00–19:00 для фондового MOEX_WEEKEND. Для FORTS/FORTS_EVENING
  нет описания указанной праздничной фазы. Переносить правила фондового рынка
  на срочный нельзя. Документ предписывает получать актуальное расписание API.
- faq_instruments описывает weekend_flag инструмента. Даже weekend_flag=true
  сам по себе не определяет семантику этой фазы и поддержку IOC.
- Попытки прочитать страницы MOEX по срочному рынку/выходным и актуальные страницы
  developer.tbank.ru/tbank.ru заблокированы сетевым шлюзом среды: tunnel 403.
  Это не ответ самой MOEX и не подтверждение её расписания. TLS не отключался.

**Итог:** семантика имени и статус точного дубликата регулярной сессии официально
не подтверждены. Ни английское название, ни одинаковые границы, ни наличие
субботы в API не достаточны для разрешения исполнения. Возможно, это алиас,
но выдавать это предположение за установленный факт нельзя.

## Решение и сведения от брокера

Оставлены прежние запреты. Не добавлены prefix/substring-эвристики, автоматическое
разрешение holiday_*, пропуск будущего дня или отключение проверок календаря.
Аукционы, клиринг и неизвестные фазы остаются заблокированы. Известные точные
дубли regular_trading_session уже объединяются в одно окно; неизвестная запись
не удаляется как «лишний дубль». Стратегия, финансовые параметры и защиты не менялись.

Брокеру через его приватную поддержку или официальную документацию нужны вопросы:

1. Является ли holiday_trading_session_morning **непрерывной регулярной торговлей**
   фьючерсами GLDRUBF в FORTS_FUTURES_WEEKEND? Или есть аукционный/иной режим?
2. Является ли запись полным семантическим алиасом regular_trading_session при
   точном совпадении границ? Может ли она приходить без regular_trading_session?
3. Допускаются ли в этой фазе LIMIT / TIME_IN_FORCE_FILL_AND_KILL (IOC/FAK) через
   T-Invest API для GLDRUBF? Нужны ли отдельные ограничения/признаки доступности?
4. Подтвердить расписание срочного рынка 21.11.2026 (10:00–19:00 MSK), исключения
   для клиринга/аукционов, timezone и семантику включения конца интервала.

Нужны официальный URL/документ либо ответ поддержки с этими определениями и
без персональных данных, а также полный **санитизированный** календарь 21 ноября
с legacy-границами и всеми intervals. Токен, account ID, SQLite и конфиг не нужны.
Общее подтверждение «торги по выходным есть» не заменяет определения API-фазы.

После такого подтверждения минимальный патч можно ограничить точным именем
и доказанным правилом alias, сохранив дедупликацию, legacy-проверки и исключения.
До этого добавление имени в regular означало бы неподтверждённое разрешение.

## Jino

Функционального обновления парсера **нет**, устанавливать исправление или менять
работающий PAPER не требуется. В отдельном клоне приёмки можно получить отчёт
и тесты: `git pull --ff-only origin feature/gldrubf-live-gated`.
На уже установленной версии 44e4261 повторить только безопасную диагностику:

```bash
sudo gldrubf-live-check calendar-diagnostics
```

Файл `/var/lib/gldrubf-live-acceptance/calendar_diagnostic.json` сохраняет только
выбранные календарные поля. Передавайте его для частного анализа. Не заменяйте
код вручную, не удаляйте запись holiday и не сокращайте диапазон запроса ради
обхода блокировки. Предыдущая инструкция обновления read-only нужна только
пользователям со старой версией, где ещё нет команды calendar-diagnostics.
LIVE не активировать; повторная диагностика сама не выдаёт торгового разрешения.

Compileall и diff check прошли. Все отслеживаемые runtime/deployment/config
файлы сравнены побайтно с 44e4261 и не изменены. Windows, CI и полный старый

holiday, обычная дедупликация известных регулярных фаз (контрольный пример),
общий current_sessions для PAPER, read-only LIVE-адаптер и запрет придуманных
holiday-алиасов. Фрагмент реконструирован по сообщению пользователя; дата-метка,
isTradingDay и legacy-envelope в тесте — явно синтетическая обвязка,
**не выдаются за оригинальный полный ответ брокера**.

Поведение PAPER и LIVE согласовано: оба сохраняют блокировку. Это проверка
совместимости защиты, не подтверждение готовности выходных торгов.
