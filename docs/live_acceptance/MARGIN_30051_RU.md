# GetMarginAttributes: подтверждённая причина 30051

19.11.2026, продолжение read-only приёмки после `f7cd69b`.

**Причина подтверждена официальным каталогом:**

> 30051 | INVALID_ARGUMENT | Account margin status is disabled
>
> Для данного договора недоступна маржинальная торговля.
> Для выставления поручений на срочном рынке, необходимо включить
> маржинальную торговлю в приложении и терминале.

[Официальный каталог Т-Инвестиций](https://russianinvestments.github.io/investAPI/errors/),
[исходный каталог официального репозитория](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/errors.md).
Свежие HTTP GET официальных errors.md, users.proto и head-users.md успешны;
[цитаты, URL и SHA256](MARGIN_30051_SOURCES.json). Авторизованные запросы Codex
не выполнял, доступа к Jino нет. Факты о реальном счёте получены от пользователя.

## Значение для данного счёта

Три успешных ответа с 15 100 RUB и нулевыми блокировками подтверждают денежные
остатки по соответствующим методам. Однако GetMarginAttributes вернул
HTTP 400 / gRPC 3 / API 30051: брокер сообщает отключённый маржинальный статус
договора выбранного счёта. Это не сообщение «денег недостаточно» и не
ошибка локального разбора схемы HTTP 200.

FULL_ACCESS относится к правам токена, а не к подключению услуги на договоре.
Ненулевой GetMaxLots и успешная оценка GetOrderPrice не отменяют требование
брокера о маржинальном статусе для поручений на срочном рынке.

Новый счёт может находиться в состоянии с неподключённой услугой; **сам возраст
счёта не установлен причиной**. Из проверенных официальных источников не следует,
что метод обязательно станет доступен через какое-либо время без действий.
Если услуга уже отображается включённой, возможную рассинхронизацию и срок
активации должен подтвердить брокер. Обещать автоматическое исправление нельзя.

## Запрос проверен

Официальный GetMarginAttributesRequest содержит единственный обязательный
`string account_id` — идентификатор счёта. В protobuf JSON это `accountId`.
Оба наших пути — Broker.account и read-only inspect_account — отправляют:

```json
{"accountId": "<явно выбранный ID счёта>"}
```

Метод: `UsersService/GetMarginAttributes`, POST к действующему REST base
`https://invest-public-api.tbank.ru/rest/tinkoff.public.invest.api.contract.v1.`;
JSON Content-Type/Accept, Bearer авторизация. Не передаются currency, UID,
номер карты, сумма пополнения или придуманный признак включения маржинальной
торговли. В примере placeholder, не реальный ID. Формат и единственный вызов
метода проверены mock HTTP-тестом. Подтверждённой ошибки запроса не найдено.

Контракт запроса не содержит правила «только старые счета» или требования
ненулевой позиции. Наш допуск отдельно требует обычный OPEN брокерский счёт
ACCOUNT_TYPE_TINKOFF и FULL_ACCESS; это политика проекта, а не доказанный полный
список поддерживаемых типов данного API-метода. Для фактической ошибки 30051
каталог прямо указывает состояние маржинальной торговли договора.

## Безопасный следующий шаг

1. В приложении/терминале проверить **выбранный выделенный счёт**, его тип и
   настройку маржинальной торговли. Не публиковать ID/скриншоты с личными данными.
2. Если услуга отключена, решение о её подключении принимает владелец счёта после
   ознакомления с условиями брокера. Наш код её не подключает и настройки счёта
   не меняет. Если услуга недоступна либо уже включена, обратиться в поддержку
   Т-Инвестиций с методом, временем ошибки и кодом 30051; данные договора —
   только в приватном канале самого брокера, без токена.
3. После подтверждения состояния брокером повторить **read-only** диагностику.
   Требуются HTTP 200 и валидные MoneyValue liquidPortfolio, startingMargin,
   minimalMargin, correctedMargin и amountOfMissingFunds, а также согласованные
   GetPositions/GetPortfolio/GetWithdrawLimits. После этого — полный check с
   GetFuturesMargin, GetMaxLots, оценкой расходов и действующими ограничениями.

**Fallback на остаток RUB не добавлен.** Даже доказанный денежный остаток не
подтверждает разрешение срочного рынка и ликвидность/маржинальные требования.
Три имеющихся метода, ГО и GetMaxLots можно сверять с отображением обеспечения
у брокера и его разъяснением, но заменять ими обязательные поля действующего
робота без документированной эквивалентности нельзя. Самый короткий безопасный
путь — устранить состояние 30051 у брокера и получить штатные маржинальные поля.
До этого account_snapshot и capital_long/short остаются заблокированы.

## Минимальное обновление на Jino

В отдельном клоне приёмки (путь может отличаться):

```bash
cd ~/mx-live-check
git pull --ff-only origin feature/gldrubf-live-gated
sudo python3 deploy/live/update_readonly.py
sudo gldrubf-live-check account-diagnostics
```

Для установки f7cd69b изменится только account_diagnostics.py: в failure появится
`reason=broker_margin_trading_disabled`, `failure_group=broker_account_restriction`,
HTTP/gRPC/API-коды и фиксированная подсказка о проверке настройки счёта.
Прочие коды не интерпретируются как 30051. Схема, баланс и ошибки других методов
остаются видны в безопасных разделах JSON. Коды и hint не содержат API body.
Обновитель знает прежний хеш этого модуля и пропускает неизменённые файлы;
неизвестный код, занятый lock и symlink по-прежнему блокируют обновление.
Конфиг, токен, PAPER, SQLite, торговое ядро и systemd не меняются.

Если остаётся 30051, следующий шаг — проверка настройки/поддержка брокера,
а не автоматические повторы или ослабление защиты. После HTTP 200:

```bash
sudo gldrubf-live-check
sudo gldrubf-live-status
```

Диагностический файл: `/var/lib/gldrubf-live-acceptance/account_diagnostic.json`.
Передавать только его для частного анализа: токен, config.json и полный ответ
API не нужны. Успешная read-only проверка не активирует LIVE.

## Проверки

**54 целевых теста прошли на Linux/Python 3.12.14 и отдельно 3.13.5**
(45 read-only приёмки, 5 обновителя, 3 исходных снимка счёта и 1 капитала).
Дополнительно обновление точной версии f7cd69b воспроизведено во временном
каталоге: заменился только account_diagnostics.py. Compileall и diff check прошли.
Сравнение SHA256 подтвердило неизменность исходных PAPER/LIVE-модулей, включая
live_api.py, risk_check в live.py и live_acceptance.py. Полный LIVE-набор,
Windows и GitHub CI в этой сессии не запускались.

HTTP в тестах имитирован, credentials синтетические. Проверены 30051 при
15 100 RUB и достаточном GetMaxLots, неизменный запрос accountId, отсутствие
подмены обеспечения и утечек, отличие иных/неполных кодов, повторная ручная
проверка после ответа брокера HTTP 200, обновление известной предыдущей версии.
[Команды и результаты](MARGIN_30051_TEST_RESULTS.txt).
Реальная повторная проверка на Jino пользователем ещё необходима; торговых
заявок, отмен, активации LIVE, deployment и merge Codex не выполнял.
