# Read-only приёмка GLDRUBF рядом с PAPER

18.11.2026, база `feature/gldrubf-live-gated` / `8c95e6f`.

**Доступа к Jino нет. На VPS ничего не развёрнуто и реальные авторизованные
ответы Т-Инвестиций не получены.** Токен в Codex не запрашивался/не использовался.
Подготовлены пользовательские команды и отдельный read-only контур.

## Реально проверено

Официальные contracts `orders`, `marketdata`, `instruments`, `operations`,
`users`, `common` прочитаны с upstream main HTTP 200. SHA256 совпадают с
зафиксированными контрактами 8c95e6f. Это подтверждение схем, **не** реальных
JSON-ответов брокера. [Источники и хеши](CONTRACT_SOURCES.json).

IOC: `TIME_IN_FORCE_FILL_AND_KILL=2` для LIMIT, частичное немедленное исполнение
с отменой остатка; отличается от FOK=3. В GetTradingStatus отдельного признака
IOC нет. Применимость к GLDRUBF/счёту/секции без заявки этими чтениями не доказать.

Проверен независимый whitelist нового клиента: PostOrder/CancelOrder/ReplaceOrder/
переводы не доходят до HTTP даже с установленным write_guard. Нет Engine/Store,
торговых permission/SQLite и сигналов. Тесты покрывают non-JSON 502, HTTP 200 с
пропущенным margin-полем, низкий капитал/лимит 1, разные ГО сторон, позицию/заявку,
закрытый рынок, старую/будущую цену, сдвиг часов, ошибки/повторный запуск,
защиту старого кэша и отсутствие утечки токена/ID счетов.
Все эти ответы — **mocks**, не доказательство работоспособности API на Jino.

Фактически выполнены **27 новых read-only тестов** на Linux/Python 3.12 и 3.13
с ResourceWarning как ошибкой, compileall, CLI help и shell syntax checks.
[Вывод проверок и SHA256 неизменённого ядра](TEST_RESULTS.txt).
Торговые команды прежнего LIVE-режима, включая разрешения и активацию, в этой
сессии не запускались. GitHub CI подготовлен; его результат не заявляется.

## Подготовлено

- `live_acceptance.py`: безопасные API-проекции, attempt/run ID, свежесть кэша,
  локальный явный выбор счёта и просмотр статистики.
- Отдельные `/opt`, `/etc`, `/var/lib/gldrubf-live-acceptance`, отдельный пользователь,
  root-owned код и root-only credential. Wrapper использует защищённый stdin.
- Installer только acceptance-файлов/команд, без systemd install/start/enable,
  LIVE ledger или разрешений; не затирает существующие файлы.
- Профиль вместо всех null: **96 h / 15 s / 30 s / ГО×3 / 2000 ₽ / 20 ₽ /
  2 ticks / 30 s / 15 s / 60 s**. Названия и объяснения:
  [инструкция](../../deploy/live/ACCEPTANCE_RU.md). PAPER и base LIVE не меняются.
- `gldrubf-live-check`, `gldrubf-live-status`; отчёт без credential/Authorization/
  имён/ID счетов/произвольного API body. Балансы остаются частными данными.

## Что осталось

Пользователю выполнить минимальные read-only команды на Jino и получить
`report.json`; проверить счёт/UID, оба ГО, RUB/пункт, доступные деньги, оценки
комиссий qty=2, GetMaxLots, портфельные поля, книгу/статусы/окна/complete-свечи.
Повторить в обычной фазе и вне её. При неизвестных полях сохранить безопасный
отчёт для подтверждённого исправления; не передавать credential/конфиг/SQLite.

Отдельно остаются принятие финансовых политик, тарифов/funding, реальное IOC,
fills/partial/cancel, торговое recovery и LIVE-backup. Без отправки заявки этот
этап не подтверждает их. `live_accepted=false` всегда, даже при зелёных чтениях.

**Решение:** пакет подготовлен, Jino/API ещё не приняты. Контролируемое открытие
двух контрактов этой проверкой не разрешено. PAPER/его SQLite/токен/systemd,
торговый LIVE, main и стратегия не изменялись. Развёртывание, торговые разрешения,
отправка/отмена реальных заявок и merge не выполнялись.
