# Точечное исправление доступа LIVE к токену

## Подтверждённая причина

По предоставленным результатам Jino, процесс gldrubf-live не может читать
master `/etc/gldrubf-live/trading-token` root:0600. Успех диагностики от root
показывает работоспособность проверенного read-path API, но не запись в SQLite
от сервисного пользователя. Прямой CLI sync по умолчанию использует master;
systemd unit уже предусматривает LoadCredential. Это разные контексты запуска.

Простое изменение на 0640 несовместимо с текущим live.secret(): он запрещает
любые групповые/прочие биты. Изменение этого fingerprint-файла потребовало бы
разбора совместимости реальной SQLite. Выбран существующий механизм
LoadCredential: master остаётся root:0600, торговый процесс не получает root.
Отдельная новая группа и новый токен не нужны.

## Изменения

- `deploy/live/manage.sh`: ограниченный запуск обслуживания через systemd-run,
  только credential-check/diagnose/sync/preflight, от gldrubf-live. Проверяет
  метаданные master и каталога, доступность config и кода. Отказывается при
  активной LIVE-службе; не останавливает её. Другие команды запрещены.
- `src/gldrubf_bot/live_credential_entrypoint.py`: предварительная проверка
  сервисного UID и доставленного credential; безопасные фиксированные категории
  ошибок (`credential_access_denied` и другие). Токен/счёт/произвольные ошибки
  и traceback не печатаются. Вывод старого sync/preflight фильтруется.
- `deploy/live/gldrubf-live.service`: подготовлен переход на тот же entrypoint
  и приватный RuntimeDirectory. Это файл для будущего согласованного обновления,
  служба не установлена и не запускалась.
- `tests/test_live_credential_entrypoint.py`: регрессии прав, секретности,
  удаления временной копии, ограничений команд и настоящего sync остановленной
  тестовой SQLite с имитацией брокера.

Некоторые версии systemd дают доступ к credential через ACL, что отражается
режимом 0440. Для совместимости с неизменным secret() entrypoint создаёт
0600-копию только внутри принадлежащего сервису RuntimeDirectory 0700;
удаляет при выходе, systemd удаляет RuntimeDirectory при завершении unit.
Для 0400 копия не создаётся. Публичные/записываемые группой файлы отвергаются.
Источник механизма ACL: systemd v255, src/core/exec-credential.c,
https://github.com/systemd/systemd/blob/v255/src/core/exec-credential.c .

Десять fingerprint-файлов идентичны 0f52907. Нет миграции, принятия старого
состояния, изменения контрольных хешей или создания новой реальной SQLite.
Install-token остаётся прежним: скрытый ввод, эксклюзивное создание 0600,
запрет перезаписи. Старые details:null в истории не переписываются; новая
команда определяет credential-ошибку до входа в прежний sync.

## Восстановление

Credential-check не обращается к брокеру. Diagnose сверяет реальные ответы
без изменения базы. Sync повторяет сверку брокера и записывает снимки в старую
базу; не очищает halt/STOP и не выдаёт разрешение. Тест сравнивает meta,
ledger_id, highwater, STOP, отсутствие permission, позиции и заявок; брокер не
получает post/cancel. Неизвестная позиция не принимается автоматически.

Resume дополнительно требует LIVE-разрешение и затем снимает остановку.
Он исключён из данной процедуры: обходить эти условия не требуется и нельзя.

Конкретные команды: [JINO_PLAN_RU.md](JINO_PLAN_RU.md).
Никаких операций на Jino, реальных API-вызовов, заявок, deployment, merge,
снятия halt/STOP и изменений PAPER при разработке не выполнялось.
