# Безопасная диагностика отказа sync

19.11.2026. База 0f52907, отдельная ветка fix/live-sync-safe-diagnostics.
Доступа к Jino нет. Реальный ответ не получен, токен не запрашивался.

## Что установлено точно

В live.py обработчик исключений записывает details только для APIError:

```python
detail = {...} if isinstance(exc, APIError) else None
store.halt('LIVE_API_DATA_OR_STATE_ERROR', ..., detail)
```

DataError, KeyError, TypeError, ValueError, ошибки файлов и sqlite3 поэтому дают
NULL. Если показанное событие успешно записано именно последним sync, details=null
указывает на эту ветку, а не позволяет определить конкретный HTTP-метод.
Стандартные HTTP/APIError обычно оставляют словарь, даже если часть полей null.
Если запись halt сама не удалась, старое событие может сохраниться — важна его дата.

**Причина потери диагностики подтверждена кодом. Причина реального отказа sync
на Jino пока не установлена. Нельзя объявлять её ошибкой операций без снимка.**

## Полный путь sync в 0f52907

1. Конфиг и private state; общая блокировка счёта и физической SQLite.
2. Версия/целостность/семантика Store, initialized marker, highwater.
3. Чтение credential; GetAccounts и OPEN/TINKOFF/FULL_ACCESS.
4. Engine.reconcile: GetOrderState для незавершённых локальных UUID (при пустом
   журнале пропускается), GetOrders, затем GetPositions/GetPortfolio/
   GetWithdrawLimits/GetMarginAttributes. Чужая/необъяснённая заявка, комиссия
   выше ограничения, расхождение позиции или blocked futures останавливают сверку.
5. Запись ACCOUNT snapshot в SQLite.
6. GetOperationsByCursor от live_meta.started до текущего UTC: проверяются echo
   счёта, временной диапазон, instrumentUid, обязательные поля, RUB MoneyValue,
   конфликты идентичности, курсоры/предел страниц.
7. Запись OPERATIONS snapshot и построение statistics, включая разбор JSON и сумм.

У preflight нет общего runner-lock пути, полной сверки заявок, загрузки операций
и итоговой статистики sync. Он проверяет счёт/ГО и пишет свои snapshots. Его успех
не доказывает успех добавленных этапов. Сам sync не требует разрешения на LIVE,
не получает TradingSchedules/GetTradingStatus или новую историю и не формирует
новые сигналы. Store.validate может перепроверять сохранённые SMA-сигналы,
если в базе уже есть бары. Прежняя ошибка API-календаря этот путь не объясняет.
Cleanup с отменой предназначен для run, не sync.

Первичный отказ до присваивания store — например, отсутствие общей папки locks
или отказ конструктора Store — сам по себе не записывает новый halt этим
обработчиком. Если событие действительно новое, приоритет гипотез смещается
к initialized marker, credential/доступу, broker reads и последующим snapshots.

## Проверяемые гипотезы для описанного плоского счёта

- GetOrders: неожиданная или неверно оформленная открытая заявка.
- Повторная account-сверка: изменившиеся поля/echo/маржинальные данные,
  broker position != ledger или blocked futures. Успешный предыдущий preflight
  подтверждает только состояние на момент того ответа.
- Операции: отсутствует/отличается brokerAccountId; дата вне запрошенного
  диапазона; instrumentUid другого инструмента; нет id/date/type/state;
  некорректны payment/commission/yield, в том числе отсутствующая валюта у нуля;
  курсор повторяется или сведения об операции конфликтуют.
- initialized/highwater или локальный write-path: права другого Linux-пользователя,
  readonly/full filesystem, ошибка SQLite, повреждённые JSON snapshots.

Пустой журнал заявок не означает пустой список операций счёта: возможны пополнения
и неторговые записи. Код запрашивает операции всего выбранного счёта, без фильтра
инструмента, но строго валидирует каждую. Финансовые проверки не ослаблялись.

Официальный operations.proto прочитан HTTP 200: accountId, from/to, limit=1000
и without* соответствуют контракту; OperationItem содержит broker_account_id.
Само наличие поля в protobuf ещё не доказывает его заполнение или совпадение
с request accountId для каждого вида операции; строгое условие исходного кода
без фактических данных не ослаблялось.
[Источник, хеш и определения](OPERATIONS_CONTRACT.json). Это не подтверждение
реальных значений из неувиденного ответа брокера.

## Минимальное исправление диагностируемости

Добавлен отдельный **diagnose_live_sync.py**, а исходные live.py/live_api.py/
live_store.py и fingerprint оставлены неизменными. Поэтому не требуется
переписывание контрольного хеша, миграция или удаление фактически созданной базы.
Обычный sync по-прежнему имеет прежний обработчик; новый инструмент предназначен
для установления причины без изменения торгового runtime.

Диагностика берёт только **существующие** lock-файлы через read-only FD/flock,
не создаёт их и не обходит занятой runner. Проверяет версию и маркеры без записи.
SQLite открывается mode=ro и копируется в :memory:. Сверка и statistics используют
те же Engine.reconcile/Store-методы, но изменяют только эту копию. Реальные
snapshot, highwater, STOP/halt и initialized marker не переписываются.
При WAL/SHM/journal рядом с базой инструмент отказывается от автоматического
восстановления; файлы не удаляет. Права проверяются по метаданным, write-проб нет.

Независимый read-seal допускает ровно восемь методов счетов/заявок/операций,
необходимых для sync. PostOrder/CancelOrder/ReplaceOrder недоступны, даже если
кто-то присвоит write_guard. Нет параметров arm/allow-live/resume или создания
торгового разрешения. Токен читается только локально существующим secret().

JSON показывает stage, фиксированную category/reason, HTTP/gRPC/API-коды,
название метода, наличие ожидаемых полей и агрегированные counts. Для операций
видны количества отсутствующих/не совпавших echo, чужих UID и не-RUB/неверных
объектов payment/commission/yield. Номера/имена счетов, UID/ID операций/заявок,
cursor, деньги, токен, Authorization, traceback и произвольный ответ не выводятся.
Неизвестное исключение даёт безопасную категорию без его текста.

Если всё чтение прошло, result=read_path_passed **не означает исправленный sync**:
остаются transient-сбой и неиспытанные записи на диск. STOP/halt не снимаются.
Проверка запущена с правами текущего Linux-процесса; иные права исходного sync
могут дать иной результат. Внешние изменения другим процессом не выдаются за
изменения самой диагностики.

## Регрессионное доказательство

Mock-сценарий буквально воспроизводит исходный CLI: init-состояние с позицией 0
и пустым журналом, preflight проходит, sync получает HTTP 200 с операцией без
brokerAccountId, возвращает 78 и записывает details=NULL. Новая команда на том же
состоянии показывает broker_operations / operation_account_echo_mismatch,
оставляя все исходные файлы побайтно неизменными. Это воспроизведение потери
диагностики, **не утверждение о конкретном ответе Jino**.

Полный набор **402 теста прошёл на Linux/Python 3.12.14 и отдельно 3.13.5**.
Windows/результат CI не заявляются. Добавлены 16 тестов: плоское halted состояние, отсутствующие поля, чужие
инструменты/позиции, повтор cursor, HTTP 502, отказы locks/версии/marker,
статистика, защита WAL, запрет mutations, отсутствие утечек и восстановление
окружения. [Команды и результаты](TEST_RESULTS.txt).

Изменённые файлы: новый src/gldrubf_bot/diagnose_live_sync.py,
tests/test_diagnose_live_sync.py и документы этой папки. Стратегия SMA20/50 DAY,
капитал/объём/расходы, PAPER, торговый fingerprint и main не изменены.

План применения требует отдельного согласования, как указано в задаче:
[JINO_PLAN_RU.md](JINO_PLAN_RU.md). Deployment, реальных операций, включения LIVE,
снятия остановки и merge в этой сессии не было.
