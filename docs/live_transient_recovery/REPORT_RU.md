# LIVE: восстановление после временных сбоев чтения

Ветка `fix/live-transient-api-recovery`, база `7210db7`.
Работа ограничена LIVE; SMA20/50 DAY, капитал 15 000 RUB, два контракта,
IOC/FAK, цены, комиссии, торговые окна и ограничения риска не изменены.
Ни VPS, ни реальные данные счёта/SQLite при разработке не использовались.

## Причина инцидентов

В исходном main временные APIError выходили из startup/цикла в общий обработчик.
Он записывал `LIVE_API_DATA_OR_STATE_ERROR`, возвращал 78; systemd содержит
`RestartPreventExitStatus=78`. Поэтому HTTP 500/70001/13 при чтении операций
становился такой же остановкой, как повреждение состояния или ошибка заявки.
Аналогично обрабатывался `GetOrders / transport_or_request_error`.
Cleanup дополнительно мог заменить первоначальную причину остановки.

## Реализованное поведение

1. LIVE Broker и его market/history read-client используют одну политику:
   максимум четыре попытки чтения, задержки с равномерным jitter
   0.5–1, 1–2, 2–4 секунды. На каждой HTTP-попытке сохраняется timeout 20 s.
   Вложенных повторов второго клиента нет.
2. Временные: HTTP 408/429/500/502/503/504 с согласованной категорией; сетевые
   тайм-ауты, DNS/соединение/обрыв ответа для разрешённых read-методов. Разрешены
   известные серверные API-коды 70001/70002/70003 и rate-limit 80002;
   противоречивые gRPC/API-коды не считаются временными. Каталог официального
   репозитория Т-Инвестиций фактически загружен: см. OFFICIAL_ERROR_CODES.json.
3. Ошибки авторизации, TLS/сертификатов, локальных прав/ресурсов, схемы/JSON,
   состояния и неизвестные классификации остаются критическими.
4. Любой временный сбой устанавливает внутренний запрет новых PostOrder.
   Даже успешный повтор не отменяет запрет. После исчерпания четырёх попыток
   процесс остаётся живым в `WAIT_API_RECOVERY`, без записи критического halt.
   Между циклами восстановления: jitter 15–30, 30–60, 60–120, 120–240,
   затем 150–300 секунд; число попыток в каждом пакете ограничено четырьмя.
5. Для продолжения нужен полный чистый проход без единого нового retry:
   физический/account lock, существующая семантическая валидация SQLite,
   fingerprint/ledger marker/highwater, отсутствие UNKNOWN/SENDING, разрешение,
   аккаунт и права, все незавершённые заявки, фактическая позиция/обеспечение,
   текущие ГО/стоимость пункта и расчёты риска LONG/SHORT, capacity, полная
   история операций и свежие завершённые свечи. Дефицит капитала не превращается
   в выдуманную ликвидацию: новые OPEN блокирует прежний риск-гейт; CLOSE
   остаётся под существующими правилами.
6. Затем перед каждой реальной отправкой остаются прежние свежие проверки
   котировки/стакана, календаря, точного UID/NORMAL_TRADING/API/LIMIT,
   позиции, обеспечения, расходов, capacity, времени и торгового разрешения.
   Кэшированное разрешение до сбоя не используется. Дополнительный guard
   запрещает PostOrder при незавершённой сверке чтения.
7. PostOrder и CancelOrder выполняются ровно одной транспортной попыткой.
   Неопределённый PostOrder остаётся UNKNOWN/критическим halt; его повторной
   отправки и автоматического снятия блокировки нет. NOT_SENT/rejection,
   частичные исполнения, TTL и идентификаторы сохраняют прежние правила.
8. Перезапуск всегда начинает с той же сверки. Ручной STOP, критический halt,
   неизвестное исполнение, расхождение позиций и просроченное разрешение не
   снимаются автоматически. Cleanup и общий обработчик сохраняют уже
   установленную критическую причину вместо её замены общим кодом.

## Операции и журналирование

Полная операция GetOperationsByCursor ранее выполнялась каждый poll, даже
при отсутствии сделок. Она не является источником текущей позиции/ГО:
для них отдельно запрашиваются заявки, исполнения и финансовые методы.
Теперь полная выгрузка от `live_meta.started` повторяется каждые 300 секунд,
при старте/восстановлении и при наличии активной локальной заявки.
Инкрементальные курсоры между выгрузками не сохраняются; старые изменения
брокера обнаруживаются следующей полной выгрузкой. Pagination, дедупликация,
проверки счёта/UID/дат не изменены. Неуспешная выгрузка не заменяет предыдущий
снимок частичными данными и блокирует новые заявки до сверки.
Это задержка отображения операций до следующего успешного опроса, а не
гарантия realtime-учёта при недоступности API. Фактические исполнения и позиция
продолжают сверяться в каждом обычном цикле.

В journald (stderr, JSON) добавлены API_READ_RETRY, API_READ_BATCH_EXHAUSTED,
API_READ_RESPONSE_RESTORED, API_CONNECTION_UNAVAILABLE,
API_CONNECTION_RECONCILED и WAIT_API_RECOVERY. В health.json указаны событие,
локальная позиция, halt, broker_state_fresh и граница последнего снимка операций.
Токен, счёт, request payload, ответ API и traceback в эти сообщения не попадают.
Stdout maintenance-команд остаётся одним безопасным JSON, в том числе при retry.
Во время backoff каждую секунду проверяются lock, STOP/разрешение и halt.

## SQLite, fingerprint, LoadCredential

Новая логика меняет `live.py`, `live_api.py`; `live_recovery.py` включён в
fingerprint. Сохранять старый fingerprint при изменившейся защите заявок было бы
неверно. Схема, Store, Strategy, PAPER и конфигурация не меняются.
Поэтому подготовлена отдельная явно подтверждаемая офлайн-операция:
`live_recovery_upgrade`. Она принимает только известный старый fingerprint
ядра 0f52907/11de6c6/7210db7 с тем же config, при отсутствии незавершённых
заявок и с полной проверкой семантики/markers/locks. Неизвестная версия
отклоняется. Создаётся приватная согласованная SQLite backup, quick_check,
SHA256, копии markers/STOP/permission и fsync. В транзакции меняется версия
и добавляется аудиторское событие; ledger_id, история, позиции и halt сохраняются.
STOP сохраняется либо создаётся; разрешение не переписывается. В run нет
автоматической миграции, принятия старой базы или автоматического resume.

Откат меняет только версию с проверкой backup и идентичности заявок/исполнений,
сохраняя текущие журналы. Он запрещён, если исполнение/заявки изменились.
Копировать старую SQLite поверх актуальной запрещено.

LoadCredential, root:0600 master, non-root entrypoint и systemd unit не меняются.
Maintenance-модуль протестирован вместе с журналированием retry.
`RestartPreventExitStatus=78` сохранён для настоящих критических ошибок.
Обычный run при временном сбое не завершается. Специальный `--once` возвращает
75, если проверка ещё не завершена, не создавая halt из-за временной сети.

## Проверки и оставшиеся риски

См. TEST_RESULTS.md. Оба инцидента воспроизведены техническими fixtures,
включая настоящий разбор HTTP 500 / code 13 / description 70001.
Это не фактический запуск на Jino и не испытание с брокерским токеном.

При длительной недоступности API открытая позиция сохраняет рыночный/маржинальный
риск. Робот не может гарантировать её закрытие без связи и не выдумывает
исполнение. Автоматическое продление разрешения отсутствует. При его истечении
робот критически останавливается. Интерактивные/внешние механизмы перезапуска
не должны удалять STOP/halt или трактовать WAIT_API_RECOVERY как разрешение.

Один запрос может задержать реакцию до сетевого timeout; urllib timeout не
является строгим дедлайном всей постраничной выгрузки. Retry-After не используется;
429 обрабатывается ограниченными backoff-пакетами, а не неограниченным циклом
быстрых запросов. Реальные длительность outages/лимиты и запись обновления в
существующую Jino SQLite требуют проверки пользователем. UNKNOWN/частичные
реальные исполнения и фактическая IOC-совместимость не проверялись реальными
заявками. Из текущих результатов нельзя утверждать успешную эксплуатацию VPS.

Инструкция обновления и отката: JINO_UPDATE_RU.md. Deploy/merge/LIVE-запуск,
отправку/отмену реальных заявок, доступ к токену и снятие остановки не выполняли.
